# 交警指挥无人车平台端功能规划与架构核验报告

> 版本：V1.8 实证收口版  
> 日期：2026-09-12  
> 依据：v11 移动端代码、既有平台静态页面、现行公开政策与标准信息  
> 适用对象：产品评审、业务评审、架构评审、UI/UE 评审、研发估算和供应商对接  
> 文档定位：本稿聚焦“移动端能力的平台化承接”和后台端开发落地。本期硬约束为移动端源码、依赖、构建、页面、入口、业务状态、交互和本地数据访问均不修改；只建设平台端Web及服务端。后台端不是移动端页面的放大版，而是按现有移动端业务逻辑建设全域指挥、统一治理、配置管理、运行监控和审计追溯；跨端运行时联动作为未来外部接入事项另行验收。

## 0. 执行摘要

### 0.1 总体结论

现有移动端已经形成“车辆监控—指令下发—任务执行—异常告警—现场反馈—事件闭环”的基本业务链，可作为平台端业务模型的重要事实来源。

平台端建设应遵循三个原则：

1. **同源**：指令、任务、告警、事件、车辆、主体单位使用统一业务编号、状态字典和数据源；
2. **上位**：平台端承担跨车辆、跨辖区、跨主体单位的统筹、配置、监控、审计和数据治理；
3. **不重复**：拍照、签名、现场说明等现场采集仍由移动端完成，平台端负责查看、内部核验和留痕，不新增“退回补充”等移动端不存在的流程。

后台开发的首要约束是：**一套领域服务、一套业务ID、一套状态机、两类客户端视图**。移动端是现场操作客户端，后台端是统筹治理客户端；两端不得各自维护指令、任务、告警、事件和反馈事实。

### 0.2 规划范围分层

| 层级 | 定义 | 处理原则 |
|---|---|---|
| 核心闭环 | 与移动端业务直接对应，缺失后无法形成指挥闭环 | 一期必须交付 |
| 平台治理 | 移动端不适合承载，但平台运行必须具备 | 一期按最小闭环建设 |
| 条件扩展 | 依赖属地监管职责、合同范围、外部数据或正式政策依据 | 条件满足后建设，不默认列为一期硬承诺 |

### 0.3 已确认的产品决策

以下决策以现有移动端逻辑为基线，优先保证核心闭环、安全性和现实可实施性。除非业务主管或安全责任单位书面变更，不再作为开放问题反复讨论。

| 决策项 | 已确认方案 | 依据与影响 |
|---|---|---|
| 直控业务语义 | 完全保持移动端现有 `accepted / rejected` 二态及 `ready_for_stop / submitting / stop_requested` 三种意图状态 | 不新增移动端业务状态，不改移动端页面和交互 |
| 网关超时处理 | 平台内部拆分传输状态 `requesting/responded/timeout/network_error`、业务结果 `accepted/rejected/null`、核实状态 `not_required/pending/verified` 和技术挂起 `safetyHold`；移动端仍使用原有二态接口 | 避免把通信异常误当业务拒绝；超时由平台服务端冻结冲突动作并进入人工核实 |
| 超时核实收口 | 核实目标动作已执行→按动作映射为现有 `stop_requested` 或 `ready_for_stop`；确认未执行→恢复调用前投影；无法核实→维持技术挂起并升级；全程保留原始网关响应和审计 | 同时覆盖急停与恢复超时，不要求移动端新增状态 |
| 普通指令任务创建 | 服务端预检通过后，在同一事务内创建 `Command(sending)`、`Task(pending_receipt)` 和投递Outbox，再异步调用主体单位 | 与移动端“先有待接收任务、再推进回执”的现有逻辑完全一致，避免有指令无任务 |
| 技术异常映射 | 业务拒绝→移动端现有“指令拒绝执行”；通信/超时→移动端现有“车辆失联/通信异常”并在后台产生系统异常 | 技术失败不得冒充主体单位业务拒绝，且不新增移动端告警类型 |
| 直控生产启用 | 直控代码可以一期建设，但生产入口必须同时满足属地授权、责任协议、车辆/主体单位能力、网关联调和有效授权快照 | 不把平台直控视为全国通用的默认行政权限 |
| 直控核实同步 | 后台核实结果通过直控状态查询和增量事件映射为移动端现有意图状态 | 不新增移动端状态，同时保证核实后跨端收敛 |
| 平台部署关系 | 作为既有城市级平台下的交警业务域建设，复用统一门户、认证和基础数据 | 避免重复建设城市平台能力 |
| 主数据关系 | 既有城市平台/准入系统维护主体单位、车辆基础数据；本平台维护指挥业务扩展和状态投影 | 车辆、企业、路网不重复建档 |
| 车辆唯一标识 | `vehicleId` 为平台唯一主键；车牌、车辆编号、设备ID、二维码为可追溯外部标识 | 二维码只映射车辆主键，支持换绑和失效 |
| 辖区权限 | 查看权按注册辖区；处置权按当前执法责任授予，跨区采用有时效的临时授权 | 兼顾跨区可见性与越权防护 |
| 普通指令范围 | 保持移动端五类指令；普通指令可单车下发，区域应急场景才允许批量建任务 | 不扩展远程驾驶和批量直控 |
| 直控范围 | 仅急停、急停恢复；不支持批量直控；资格以配置和能力快照判定 | 与移动端直控边界一致 |
| 告警模型 | 主状态维持“待响应/已归档”；响应阶段、在途任务、待反馈为只读投影 | 不破坏移动端两态告警逻辑 |
| 事件模型 | 事故、故障、道路障碍均可只上报；区域任务为可选项；事件人工闭环 | 保留移动端前置条件和边界 |
| 现场反馈 | 移动端负责采集和追加；平台端只读查看、内部核验并留痕，不退回、不改写原始反馈 | 保持现场证据来源唯一，避免新增移动端流程 |
| 身份认证 | 优先接入公安/城市平台统一认证，平台补充MFA、设备会话和强制下线 | 避免独立账号体系形成安全孤岛 |
| 值班协同 | 按单席试运行/多席轮班两种运行模式配置，不按人员数量硬编码裁剪 | 小团队仍保留责任和在途快照；只有实际存在多人协同时启用分派、升级和双签 |
| 合规扩展 | 违法线索、证据包、企业门户、DSSAD、OTA等按属地职责、数据源和合同条件建设 | 不作为移动端核心闭环的一期硬承诺 |
| 一期规模 | `N_prod`取权威车辆清单，`N_cap=max(2×N_prod, N_prod+24个月书面新增量)`；并发和吞吐按12章公式计算 | 可立即用于研发估算；真实清单只代入参数，不改变架构 |

### 0.4 待补齐事项的收口原则

本版不再把所有未知项笼统写成“待确认”，而是按是否能在产品方案阶段科学确定进行三类收口：

| 类别 | 处理方式 | 本版结果 |
|---|---|---|
| 产品与逻辑决策 | 依据现有移动端代码、行业通行机制和最小安全闭环直接定版 | 页面边界、状态机、数据对象、接口语义、异常出口、责任流和验收规则全部冻结 |
| 工程默认值 | 在没有更严格合同或环境约束时直接采用；后续变更必须走基线变更 | 组件体系、契约版本、时间规范、容量计算、性能目标、恢复目标和分层留存已给出默认值 |
| 外部事实输入 | 不虚构数值或权限；给出责任人、输入物、截止门禁和缺失时的系统行为 | 真实车辆清单、外部接口、统一身份、属地直控授权、信创清单和合同SLA转为“生产放行输入”，缺失即按明确降级或关闭处理 |

因此，文档中仍保留的“无法核验”是事实状态，不是方案缺口；仍需外部提供的参数也不再阻塞后台页面、领域模型和接口研发，只阻塞相应生产能力的联调或放行。

### 0.5 V1.7补丁清单的独立复核结论

本节把《V1.7补丁清单-实证与遗漏项-20260912.md》作为外部审查材料，而不是产品指令或已验收证据。逐项回到当前代码核验后，结论如下：

| 外部建议 | 独立判断 | 本版处理 |
|---|---|---|
| 直控二态受到回归脚本约束 | **成立**。脚本明确迁移旧unknown记录并断言页面不得出现未知态UI | 将“二态业务契约+现有迁移测试”同时列为基线；以后若变更必须同步评审契约、迁移策略和测试，不得只改页面 |
| 回归10次9次通过、确认弹窗约10%不稳定 | **本轮未复现，不能当作本稿实证**。可见脚本在确认弹窗处采用5秒等待，只能证明该处是候选脆弱点 | 列为BE-01测试基线核验项；先定位页面就绪条件，再决定修产品或修测试，未复现前不写固定失败率 |
| 既有平台静态页“待确认”永远筛不出结果 | **不成立**。页面代码已把“待确认”映射为`sending/accepted/executing` | 不按死筛选修复；改为“处理中”聚合并允许下钻三种实际回执，或直接按六态筛选 |
| 既有平台静态页把六态回执称为执行状态 | **成立** | 明确该页不是生产基线；新后台分开显示“回执状态”和“任务状态” |
| 静态页7天种子数据低于留存要求 | **不成立**。演示样本跨度不能证明后端留存实现 | 生产留存只按12.1的数据分层、归档和恢复证据验收 |
| `chan`字段导致跨端失败 | **部分成立**。字段名与规范`dispatchChannel`不一致且当前页面未形成可靠契约，但不是已证实的数据丢失 | 新契约统一`dispatchChannel`；静态页不做生产兼容承诺 |
| 操作员全角括号造成跨端比对失败 | **问题归因不成立**。显示文本不应参与身份匹配 | 强制使用`operatorId/policeNo`匹配，括号仅属视觉文案 |
| 同车型全归一家企业 | **成立于当前Mock，不可用于生产** | 显式禁止`getEnterpriseByVehicleType()`进入生产归属判断；按`vehicleId`读取权威主数据 |
| 事件种子企业名与企业字典完全不重叠 | **成立于当前种子**；“所有企业统计必为空”仍取决于具体联表方式，不能无证据扩大 | 种子在演示前统一；生产导入做企业主键映射和对账，不按名称联表 |
| 蓝图三项指令与现行五项字典不一致 | **成立，但蓝图是历史设计稿** | 当前业务字典为唯一现行口径；蓝图只能作历史参考，不重新打开指令范围 |
| `<5min/<30min`注释不是法规SLA | **成立** | 视为演示提示，禁止直接进入生产计时、升级和合同验收 |
| 小团队取消值班/交接治理 | **不宜按人数阈值决定**。安全关键业务即使2至3人也可能跨班 | 按运行模式分层：单席试运行保留在途快照/导出；多席轮班启用签收、分派、升级和双签，不按人数硬编码 |
| 非成功反馈必须有owner和SLA | **成立** | 生成或维持有负责人、下一动作和到期时间的WorkItem；缺正式SLA时由受理人选择到期时间并记录依据，不冒充法定时限 |

复核后的净结论是：V1.7主体架构无需推翻；V1.8补齐既有平台页定性、测试基线、种子数据禁用项、历史口径优先级和非成功反馈责任时限，同时纠正“死筛选、7天即留存不足、显示括号导致跨端失败”等不成立推断。

## 1. 设计依据与边界

### 1.1 代码事实

移动端主要入口与能力如下：

| 移动端入口 | 主要能力 | 平台端设计影响 |
|---|---|---|
| `/console` | 地图监控、车辆选择、扫码定位、普通指令、急停/急停恢复 | 建设实时监控、指令调度、直控和车辆身份管理 |
| `/tasks` | 任务列表、状态跟踪、撤回、异常终止、现场反馈 | 建设全域任务台账、超时管理、反馈查看/核验和关联追踪 |
| `/notices` | 车辆失联、故障停驶、指令拒绝执行 | 建设统一告警工作台、升级路由和关联处置 |
| `/emergency` | 事故/故障/道路障碍上报、关联车辆、可选区域任务 | 建设事件台账、区域处置批次和人工闭环 |
| `/profile` | 操作日志、指令记录、推送偏好、密码、登录设备 | 建设统一身份、会话设备、通知路由和审计能力 |

当前统一业务字典包括：

- 普通指令：减速、靠边停车、启动行驶、快速驶离、远程接管；
- 平台直控：急停、急停恢复；
- 任务状态：待接收、已接收、执行中、已完成、异常终止、已撤回；
- 主体单位回执：发送中、主体单位已接收、执行中、执行完成、执行异常、已撤回；
- 告警类型：车辆失联、故障停驶、指令拒绝执行；
- 告警生命周期：待响应、已归档；
- 应急事件：交通事故、车辆故障、道路障碍。

### 1.1.1 移动端不改动的硬约束

“移动端不改动”在本期定义为：不修改移动端源码、依赖、构建配置、页面入口、用户操作路径、业务指令名称、任务/告警/事件主状态、现场反馈交互和本地数据访问代码。本期只建设平台端Web、平台服务端、领域模型、兼容API、事件服务、数据库、外部接口适配和后台验收。

1. **平台先行，移动端不在本期改造**：平台服务端提供与现有移动端业务语义兼容的API、事件和错误码，作为未来外部联调的接口基线；不在本期向移动端注入Adapter、不修改移动端localStorage/Mock调用，也不把浏览器本地数据当生产事实源；
2. **平台技术字段不外溢**：`gatewayTransportStatus`、`gatewayBusinessResult`、`verificationStatus`、`safetyHold` 等仅用于平台安全治理、审计和人工核实，不新增移动端可见业务状态；`safetyHold` 仅表示结果不确定时的技术挂起，不等同于移动端 `stop_requested` 急停意图状态；
3. **平台新增域不反向污染移动端字典**：合规线索、证据、OTA、DSSAD、数据质量等平台独有事件，不直接作为移动端新的告警类型、任务状态或事件类型推送；
4. **服务端是跨端最终裁决者**：即使移动端本地状态显示可操作，平台服务端仍须重新校验权限、车辆状态、在途冲突和安全锁；
5. **技术超时的兼容处理**：直控网关超时由平台记录技术挂起并冻结冲突动作；只有核实目标动作是否执行后，才将结果映射为移动端现有的 `accepted/rejected` 和 `ready_for_stop/stop_requested` 状态；无法核实时保持技术挂起并升级；
6. **不改变用户认知**：移动端仍使用“已下发/下发失败/紧急控制下发中”等既有文案，平台端另外展示技术异常和核实进度，避免移动端出现无法理解的新状态。

> **现实边界**：当前移动端代码核验显示，车辆、指令、任务、告警、事件、反馈和直控主要依赖localStorage/MockWS，未发现已接入本平台的HTTP API、SSE或WebSocket生产契约。因此在“移动端源码完全不改、仅开发平台端”的本期范围内，平台可以完成对应服务端和后台能力，但不能宣称当前移动端运行时已经与平台实时联动。跨端真实闭环只能在后续另立“外部接入/部署配置”事项，并证明既有移动端已有可切换服务端契约或由项目方批准移动端改造后，方可验收；本期不得偷偷把该工作计入后台完成度。

### 1.1.2 既有平台静态页面的定性与处置

当前仓库中的`投标演示页面/交警指挥指令日志.html`是可交互的前端静态演示页，使用内置数组、客户端筛选/分页和固定回执字典，没有证明真实API、权限、服务端分页、审计、跨端同步或数据留存已经实现。它可以提供视觉和字段参考，但**不得作为V1.8后台实现或验收基线**。

独立审计结论：

| 项目 | 当前事实 | 风险等级 | 收口要求 |
|---|---|---:|---|
| “待确认”筛选 | 实际聚合`sending/accepted/executing`，不是失效筛选 | 中 | 新后台改名“处理中”，旁示数量并支持下钻实际回执；正式查询参数仍传回执枚举 |
| 状态列 | 六种主体单位回执统一标成“执行状态” | 高 | 列名改为“回执状态”；任务状态仅在关联任务区展示，二者禁止复用字段 |
| 主体术语 | 使用“车企已接收/车企执行中” | 中 | 按移动端现行字典统一为“主体单位已接收/执行中”，企业类型仅作主体属性 |
| 渠道字段 | 演示数据使用`chan:"platform"`，与统一字段`dispatchChannel`不一致 | 高 | 生产Schema只接收`dispatchChannel=enterprise/direct`；不得把静态字段直接迁库 |
| 数据与分页 | 7天固定样本、浏览器内扩展和分页 | 高 | 新后台必须使用服务端查询、稳定排序、游标或页码契约；样本跨度不得当作留存证据 |
| 人员字段 | 页面拼接姓名与警号用于展示 | 中 | 数据层使用`operatorId`和`policeNo`，展示格式不得参与查询关联或审计身份 |

### 1.2 平台职责边界

术语约定：本文“后台端/平台端”指PC管理平台及其支撑能力，“服务端”指API、领域服务、异步任务和数据存储。二者不是同义词；本期后台页面统一经过服务端读写同一业务事实，现有移动端继续按当前演示方式运行，不把尚未发生的跨端运行时联动写成已完成能力。

| 能力 | 移动端 | 平台端 | 主体单位/车端 |
|---|---|---|---|
| 现场发现与上报 | 主责 | 查看、统筹 | 配合 |
| 普通指令发起 | 可发起单车指令 | 可发起单车指令；仅应急区域场景按车批量建任务 | 确认并组织执行 |
| 急停直控 | 经授权后发起 | 经独立授权后发起 | 网关受理、车端安全联锁 |
| 任务反馈 | 现场采集和追加 | 只读查看、内部核验 | 提供执行回执 |
| 告警处置 | 响应、现场干预 | 分派、升级、监督、归档 | 提供状态与人工兜底 |
| 基础数据 | 查询 | 统一视图和业务扩展 | 提供权威源数据 |
| 配置与权限 | 不承担 | 主责 | 不承担 |
| 审计与证据 | 产生操作记录 | 统一留存、检索、导出 | 提供原始回执或车端记录 |

### 1.3 明确不做

- 不建设远程驾驶、方向盘遥控或车辆轨迹手工修改；
- 不把主体单位回执改写为交警对车辆执行结果的直接确认；
- 不在平台端重复实现移动端拍照、签名等现场采集；
- 不自动作出违法认定、责任认定或处罚决定；
- 不允许前端绕过权限、状态机和安全校验直接调用车企接口或直控网关；
- 不允许批量急停或批量解除急停；
- 不以演示数据、Mock 结果或静态页面替代真实接口验收。

### 1.4 问题陈述

现有移动端适合单个民警在现场快速监控、下发指令、处理任务和提交反馈，但无法独立承担多人轮班、跨辖区统筹、统一配置、数据质量、接口健康、权限治理和全局审计。若直接复制移动端页面到桌面端，会形成两套数据和两套状态；若继续以 localStorage/Mock 为事实源，又无法支撑跨设备、跨席位和真实主体单位协同。

因此，本平台要解决的不是“缺少PC页面”，而是以下三个根问题：

1. **全局看不全**：单个移动端只能看到本地视图，值班长无法统一识别无人负责、即将超时和跨主体单位的事项；
2. **跨端管不住**：权限、在途冲突、直控安全锁、字典和配置如果只在前端判断，多设备并发时无法保证一致；
3. **事后说不清**：指令、任务、告警、事件和反馈缺少统一服务端关联时，难以完整回答“谁在何时基于什么数据做了什么、结果如何、异常如何收口”。

平台端的产品目标是：在不改变移动端业务逻辑和用户路径的前提下，把移动端已有闭环提升为可由多人协同、服务端裁决、统一监控和完整审计的城市级指挥闭环。

一一对应不等于两个端展示完全相同字段，而是必须满足以下不变量：

1. 同一业务事实使用同一主键、同一服务端状态机和同一审计链；
2. 移动端只展示现有业务状态，后台可以展示技术状态和治理字段，但不得反向污染移动端枚举；
3. 本期后台端所有写操作进入同一领域服务；未来移动端接入时也必须进入该领域服务，不允许分别写库后再离线合并；

5. 任何客户端缓存都只是投影；冲突时以服务端版本为准，并向用户说明刷新原因。

## 6. 核心业务流程

### 6.1 告警—指令—任务—反馈—归档

```text
系统/主体单位产生告警
        ↓
告警进入统一工作台
        ↓
民警响应或值班长分派
        ↓
进入车辆详情并选择处置方式
        ├─ 普通指令 → 原子创建发送中指令+待接收任务 → 主体单位接收/执行回执
        ├─ 直控急停 → 直控网关 → 移动端仍显示受理/拒绝；技术超时由平台挂起核实
        └─ 人工联系 → 记录联系人、时间和结果
        ↓
移动端提交现场反馈
        ↓
关联任务已完成且反馈为成功
        ├─ 是 → 按移动端现有逻辑自动归档关联告警
        └─ 否 → 告警保持待响应/已响应展示，继续处置或人工说明后归档
```

前置条件：车辆可识别、操作人有辖区和动作权限、数据新鲜度可判定、无冲突在途动作。

后置结果：形成告警、指令、任务、反馈、审计之间的业务编号关联；任何失败都保留原因码和人工兜底入口。

边界条件：消息送达不等于已响应；主体单位接收不等于车辆已执行；**仅任务完成仍不归档，必须同时存在成功的现场反馈**；异常或部分完成反馈不自动归档。

### 6.2 普通指令

1. 服务端校验用户、辖区、车辆状态、主体单位通道、数据新鲜度和在途冲突；预检不通过时不创建业务记录；
2. 使用 `clientRequestId` 做幂等判定；相同请求号返回已创建的同一组业务ID；
3. 在同一数据库事务内创建 `Command(sending)`、`Task(pending_receipt)`、二者关联关系和 `OutboxMessage`；任何一项失败则整体回滚；
4. 事务提交后由Outbox工作器调用主体单位接口，前端只显示“已提交/待接收”，不得等待外部接口完成后才创建任务；
5. 主体单位通过回调推进 `accepted → executing → succeeded/failed`，任务同步映射为 `received → executing → completed/abnormal`；
6. 回调丢失时通过主动查询和定时对账补偿，迟到/重复/乱序回调按消息ID和状态版本幂等处理；
7. `sending/accepted` 可以撤回，`executing` 后禁止撤回，只能发起明确反向指令；
8. 通道重试截止前任务保持待接收并显示剩余时限；超过截止时间才进入异常终止，不提前伪造业务拒绝；
9. 失败原因必须分类映射到移动端现有任务和告警类型，同时保留平台系统异常。

| 原始失败类别 | 任务终态 | 移动端现有告警类型 | 后台额外处理 |
|---|---|---|---|
| 主体单位明确拒绝 `enterprise_rejected` | `abnormal` | `rejected` 指令拒绝执行 | 保存拒绝原因和原始回执，可在原因解除后重新发起 |
| 通信超时/网络异常 `transport_timeout/network_error` | 重试截止前保持 `pending_receipt`；截止后 `abnormal` | `offline` 车辆失联/通信异常 | 创建SystemIncident/DeliveryException并启动通道对账 |
| 车辆故障/执行失败 `vehicle_fault/execution_failed` | `abnormal` | `fault` 故障停驶 | 关联车辆故障信息和主体单位执行回执 |
| 回调缺失但主动查询得到终态 | 按查询结果映射 | 按最终原因分类 | 标记对账补偿来源，不重复创建任务或告警 |

### 6.3 平台直控急停/恢复

直控属于技术能力与治理授权同时成立后才能开放的条件型生产动作。后台可以在一期完成代码建设和隔离环境测试，但生产按钮必须由服务端按以下条件动态下发，不得只靠前端配置显示：

- 属地制度或项目文件明确交警平台、主体单位、网关方和安全员的责任边界；
- 车辆、主体单位、辖区、动作类型、网关协议和能力版本均在有效授权范围；
- 车辆/主体单位仍保留必要的车端安全联锁和拒绝能力，平台不得绕过车辆自身安全机制；
- 直控网关完成双向认证、幂等、超时、迟到响应、查询核实和审计联调；
- 当前操作者具备直控独立权限、处置权和强认证；
- 任一条件失效时，服务端立即关闭 `availableActions` 中的直控动作。

每次直控必须保存 `DirectControlAuthoritySnapshot`。网关 `accepted` 只表示直控请求已被明确接受并进入现有 `stop_requested/ready_for_stop` 意图投影，不得在后台文案中表述为“车辆已停止”或“车辆已启动”。

建议服务端顺序：

```text
强认证和独立授权
    ↓
核验车辆、能力快照和目标动作
    ↓
按车辆状态版本执行 CAS 占位
    ↓
写 submitting 记录
    ↓
调用直控网关
    ↓
移动端业务结果：accepted / rejected
    ↓
平台传输状态：gatewayTransportStatus=requesting / responded / timeout / network_error
平台业务结果：gatewayBusinessResult=accepted / rejected / null
    ↓
更新急停意图、技术挂起、审计和人工核实事项
```

强制规则：

- 不得先调用网关后抢锁；
- 急停和恢复必须关联目标急停记录；
- 急停恢复只表示解除平台急停锁，不表示车辆已经启动；
- 网关超时不得直接向移动端伪造“急停已下发”或“车辆已停止”；
- 网关超时写入 `gatewayTransportStatus=timeout`、`gatewayBusinessResult=null`，设置 `verificationStatus=pending`、`safetyHold=true`，冻结该车与目标动作冲突的指令并生成人工核实事项；
- 核实确认目标动作已执行后：急停映射为现有 `stop_requested`，急停恢复映射为现有 `ready_for_stop`；确认目标动作未执行则恢复调用前投影，并记录现有 `rejected` 结果；
- 核实仍无法确认时维持 `safetyHold=true`，升级值班长和人工联系，不得通过重复调用网关“试出结果”；
- 超时后到达的迟到响应只作为核实证据写入，不自动覆盖已创建的核实事项或清除技术挂起；
- 人工核实须记录核实人、独立复核人、核实方式、核实时间、网关原始响应和最终解锁依据；同一人不得自核自批；
- 只有双人结论一致或值班长完成独立复核后才能清除 `safetyHold`；当班无法取得第二复核人时，只能维持挂起、升级和转线下确认，不能单人解锁；
- 直控只生成指令记录、技术尝试记录和必要的核实事项，不生成普通任务，不触发新的移动端告警类型；
- 前端按钮禁用只是体验，服务端必须再次阻断。

| 网关状态 | 移动端结果/意图投影 | 技术挂起 `safetyHold` | 是否允许重试 | 后续动作 |
|---|---|---|---|---|
| 明确受理急停 | `accepted / stop_requested` | 否 | 否 | 写入现有直控指令记录，急停业务意图保持生效 |
| 明确受理恢复 | `accepted / ready_for_stop` | 否 | 否 | 解除急停业务意图；不自动发起启动行驶 |
| 明确拒绝 | `rejected`，恢复调用前投影 | 否 | 原因解除后可用新请求号重试 | 记录拒绝原因 |
| 超时/网络异常 | 返回现有错误，不新增状态；暂保持调用前可见投影 | 是 | 否 | 平台生成核实事项并阻断冲突动作 |
| 核实确认目标动作已执行 | 急停→`stop_requested`；恢复→`ready_for_stop` | 否 | 否 | 记录双人核实依据并关闭核实事项 |
| 核实确认目标动作未执行 | `rejected`，恢复调用前投影 | 否 | 是，使用新请求号 | 记录双人核实依据并关闭核实事项 |
| 核实仍无法确认 | 返回现有错误，保持调用前可见投影 | 是 | 否 | 升级值班长、人工联系和持续核实 |

核实结果的联调契约：后台完成核实后更新 `DirectControlState.stateVersion`，发布 `direct-control.changed`；平台提供现有移动端可理解的投影Schema和测试夹具。由于本期不修改移动端源码，不能把事件消费、重新进入车辆详情、应用恢复或断线重连后的运行时收敛写成已实现能力；该项作为后续外部接入验收门禁。技术字段和核实过程不向移动端展示。

### 6.4 应急事件与区域处置

1. 交通事故、车辆故障、道路障碍均允许只上报事件；
2. 只有存在 GPS、人工选点或车辆位置锚点时，才能创建区域任务；
3. 对每辆车独立预检，并复用6.2普通指令事务创建该车的 `Command+Task+Outbox`；批次只汇总逐车结果，不直接越过指令服务写任务；
4. 批次部分成功时不回滚已成功任务；
5. 事件可以在说明未完结任务风险后人工闭环；
6. 事件闭环不自动修改仍在执行的任务。

### 6.5 值班与交接班

值班治理按**运行模式**启用，不按人数写死阈值：

| 运行模式 | 最小能力 | 不建设内容 | 启用条件 |
|---|---|---|---|
| 单席试运行 | 自动生成在途事项快照、导出、未完成事项责任人、下次登录续办 | 不建设复杂排班、逐级分派和双人交接流程 | I-02确认单席连续负责，且直控生产入口关闭或另有安全复核机制 |
| 多席/轮班运行 | 我的待办、队列认领、分派/转派、升级、交接双方确认、值班长总览 | 不预置与实际组织无关的多级层级 | 存在换班、多人并行、跨辖区协同或直控生产操作任一情形 |

即使只有2至3名人员，只要存在跨班或安全关键操作，也不能仅以“人少”为由取消责任和交接留痕；反之，单席试运行不应为了形式完整引入完整排班管理。

交班清单必须自动聚合：

- 未响应告警；
- 在途指令和任务；
- 网关超时待核实事项（平台技术状态，不新增移动端业务状态）；
- 通道故障；
- 已完成/异常终止但尚未提交现场反馈的任务；
- 临时权限和临时 ODD 授权。

多席/轮班模式下，交接完成后由交接双方确认，记录时间、席位、事项快照和遗留说明。单席试运行下保存不可覆盖的收班快照，并在下一班次/下次登录展示未完成事项；两种模式都不得因“完成交班”自动关闭源业务对象。

### 6.6 业务闭环总矩阵

| 链路 | 触发源 | 平台责任 | 移动端承接 | 异常出口 | 闭环判据 |
|---|---|---|---|---|---|
| 车辆监控 | 遥测/主体单位状态 | 聚合、展示新鲜度、乱序丢弃、异常发现 | 地图和车辆详情保持现状 | 数据过期→禁止操作并进入通道/数据质量待办 | 状态恢复或异常已有责任人和处理记录 |
| 普通指令 | 移动端或平台单车发起 | 事务内创建指令+待接收任务+Outbox，完成鉴权、幂等、在途冲突、主体单位调用和回调对账 | 五类指令、待接收任务和现有回执展示不变 | 业务拒绝→rejected；通信超时→offline+系统异常；车辆故障→fault；均可人工联系或继续处置 | 执行完成/异常/撤回形成终态，指令、任务、告警和审计可追溯 |
| 直控 | 移动端或平台授权人员发起 | 版本锁、网关调用、急停意图控制、技术挂起与超时核实 | 保持二态结果和现有三种意图状态 | 超时→平台技术挂起，禁止重复网关调用；无法核实则升级 | 明确结果或核实后映射为现有 `stop_requested`/`ready_for_stop`；无法核实时持续挂起且责任明确 |
| 任务反馈 | 任务在指令提交时创建，主体单位回执推进其进入终态 | 保存任务、反馈历史和内部核验标记；非成功反馈生成/维持带负责人、下一动作和`dueAt`的WorkItem | 已完成/异常终止后提交或追加反馈 | 部分/失败反馈→保留待跟进，不自动关闭告警；到期未处理→升级 | 成功反馈留痕；关联告警按现有逻辑自动归档；非成功事项只有风险解除或被后续事项承接后才能关闭 |
| 告警处置 | 系统、主体单位、指令或任务异常 | 统一队列、分派、升级、关联指令/任务、归档 | 响应和进入指挥控制保持现状 | 无法远程处置→人工联系并记录结果 | 成功反馈自动归档，或平台人工说明后归档 |
| 应急事件 | 移动端事故/故障/障碍上报 | 事件台账、区域批次、任务关联、风险汇总 | 上报、选车、照片和人工闭环保持现状 | 无区域锚点→只上报；车辆有在途任务→逐车跳过 | 人工闭环说明完成，关联任务继续独立跟踪 |
| 配置治理 | 管理员提交配置 | 校验、影响分析、审批、发布、监测、回滚 | 不新增移动端配置入口 | 发布失败→保持旧版本；异常→回滚 | 新版本生效并有审计，或成功回滚至旧版本 |
| 权限治理 | 组织/人员/值班变化 | 授权、临时授权、到期回收、审计 | 不改变现有业务入口 | 越权→服务端拒绝并返回现有可识别错误 | 权限生效/失效与审计记录一致 |

闭环判定原则：每条链必须同时具备“事实记录、责任人、当前状态、下一动作、异常出口、终态依据和审计记录”；缺少任意一项，只能称为页面可用，不能称为业务闭环。

## 7. 状态机与业务口径

### 7.1 普通指令回执

```text
sending → accepted → executing → succeeded
   │          │           └──────→ failed
   │          └──────────────────→ failed
   └─────────────────────────────→ failed

sending/accepted → recalled
executing 后禁止 recalled
```

### 7.2 任务状态

```text
pending_receipt → received → executing → completed
       │             │           └→ abnormal
       │             └────────────→ abnormal
       └──────────────────────────→ abnormal

pending_receipt/received → recalled
```

任务主状态和主体单位回执必须分开存储、分开展示。回执用于描述通信和执行过程，任务状态用于描述业务工作进度。

| 主体单位回执 | 对应任务状态 | 说明 |
|---|---|---|
| `sending` | `pending_receipt` | 请求已提交，尚未确认送达 |
| `accepted` | `received` | 主体单位已接收，不代表车辆执行 |
| `executing` | `executing` | 主体单位已确认组织执行 |
| `succeeded` | `completed` | 已收到执行完成结果，可进入现场反馈 |
| `failed` | `abnormal` | 拒绝、失败或业务超时，需继续处置 |
| `recalled` | `recalled` | 仅允许在执行前撤回 |

### 7.3 告警状态

- 可写主状态：`pending / resolved`；
- `unread`、是否已响应、是否在途、是否待反馈等均为事件投影；
- 平台页面可显示派生的 `responseStage`，但不得作为另一套可写状态；
- 关联任务为 `completed` 且移动端现场反馈为 `success` 时，按现有移动端逻辑自动归档关联告警；
- `partial/failed` 反馈、任务异常终止或任务撤回时不自动归档，保持已响应并继续处置；
- 平台人工归档不新增状态，只能在已响应后选择“重复告警、数据误报、人工核实风险解除、已转事件/后续事项”等结构化原因并填写依据；若仍有关联在途任务或风险，必须关联继续承接的Incident/WorkItem，不得通过归档隐藏未完事项。

### 7.4 应急事件状态

- 内部状态：`reported / handling / closed`；
- 移动端可以把 `reported/handling` 统一展示为“已上报”；
- 平台端可以显示处置阶段，但不得把关联任务完成自动等同于事件闭环。

### 7.5 平台治理对象状态

| 对象 | 状态机 | 闭环规则 |
|---|---|---|
| WorkItem | `open → claimed → resolved`；可在原因解除前 `claimed → open` 重新分派 | 只在源对象不再需要下一动作或已生成后续待办时关闭，不允许用关闭待办替代关闭告警/任务/事件 |
| VerificationCase | `pending → verifying → resolved` | `resolved` 必须包含 `executed/not_executed/unable_to_verify` 结论、核实人、独立复核人和证据；无法核实时业务安全锁继续保持 |
| NotificationDelivery | `pending → sending → delivered/failed`；可按策略 `failed → sending` | `delivered` 仅代表渠道送达；用户已读和业务已响应作为独立时间字段，不由送达状态推断 |
| ShiftHandover | `draft → submitted → accepted`；接收前可 `canceled` | `accepted` 需要交接双方身份和快照摘要；交接完成不自动关闭、转移或改写源业务状态 |
| ConfigRelease | `draft → validating → pending_review → approved → publishing → published/failed`；已发布可产生新版本 `rolled_back` | 提交人与复核人分离；失败继续使用旧版本；回滚是新发布记录，不删除原版本 |
| SystemIncident | `open → acknowledged → mitigating → resolved → closed` | 必须有责任人、影响范围、补偿结果和验证证据；系统故障关闭不自动把受影响业务记录改为成功 |

平台治理状态不得直接下发为移动端新任务、告警或事件枚举。移动端只接收由领域服务计算出的现有业务状态和可识别错误。

### 7.6 状态和字典版本

每条业务记录至少保存：

- `schemaVersion`；
- `dictionaryVersion`；
- `stateMachineVersion`；
- `createdAt`、`serverAt`；
- `correlationId`；
- 关键规则或配置快照 ID。

历史记录按产生当时的字典和状态机解释，不因后续配置改变而回写。

SLA/处置时限也必须按版本管理，至少保存`ruleId, ruleVersion, sourceType, sourceRef, effectiveFrom, effectiveTo`。`sourceType`只能为`law/policy/contract/project_rule/manual`之一；页面同时展示时限、依据和生效时间。当前代码注释中的“紧急<5min、高<30min”没有来源引用和版本，只能视为演示提示，不能写入生产规则、自动升级阈值或验收结论。正式规则缺失而事项又必须跟进时，由受理人选择`dueAt`并记录`dueAtSource=manual`，平台仍执行到期提醒和升级，但不得标称“法定超时”。

### 8.3 数据质量门禁

必须持续检测：

- 车牌与车辆编号冲突；
- 车辆—主体单位关系由车型默认推断、企业名称未映射主键或关系有效期缺失；
- 离岗/冻结用户仍有有效授权、临时授权过期未回收、班次无值守人；
- 车辆与主体单位关系缺失；
- 旧编号和旧指令名称；
- 坐标越界或跳点；
- 车端时钟漂移；
- 遥测乱序、重复、缺失；
- 指令、任务和回执不一致；
- 指令已创建但任务或outbox缺失、任务无源指令、同一请求产生多组业务ID；
- 告警关联任务缺失、已归档告警不满足闭环条件；
- 待办无人负责、已逾期无升级动作、交接快照与在途事项不一致；
- 直控授权快照缺失、过期或与车辆/动作/辖区不一致；
- 通知偏好与实际送达结果不一致、关键通知持续失败；
- ODD或资质过期；
- 历史记录缺少字典版本。

异常数据不得静默修正，必须保留原值、修正值、责任人、时间和影响范围。

生产导入门禁：`vehicleId/enterpriseId`、标识有效期、来源系统、源记录版本和导入批次缺一不可；导入前输出总数、成功数、拒绝数、重复数、孤儿关系数和逐项原因，导入后以车辆、企业、辖区三个维度对账。演示种子不得与生产库做增量合并。

### 8.4 一致性约束与索引

- `vehicleId` 全局稳定；同一时段内，同类型 `VehicleIdentifier` 的有效值只能映射一辆车，换绑必须先结束旧有效期；
- 普通指令按调用方和 `clientRequestId` 建唯一约束，`Command.taskId` 与普通任务一一对应；直控尝试单独建模，不误生成普通任务；
- `OutboxMessage` 按聚合对象和事件版本唯一，消费方按 `messageId` 幂等；投递失败只增加尝试记录，不复制业务对象；
- 状态更新必须同时匹配主键和 `stateVersion`，受影响行数为0即返回409并携带服务端当前版本；
- 反馈按 `taskId+version` 唯一且只追加；告警按“来源+来源事件ID+规则版本”去重，禁止仅用时间窗口粗暴合并；
- 业务表通过外键或等价应用约束保证指令—任务—告警—事件—反馈关联有效；审计和原始报文不得级联删除；
- 高频查询至少覆盖“辖区/状态/责任人/发生时间”“车辆/时间”“主体单位/状态/时间”等组合索引，最终索引以真实查询计划和压测结果调整；
- 若未来一套部署承载多个城市或项目，所有业务主键、唯一约束、权限决策和对象存储路径必须加入不可伪造的项目隔离键，不能只依赖前端传参隔离。

## 9. 权限与安全控制

### 9.1 三层权限

1. 功能权限：是否可进入页面或使用功能；
2. 数据权限：可以查看哪些辖区、车辆和主体单位；
3. 操作权限：是否可以下发、撤回、直控、归档、导出或修改配置。

### 9.2 关键权限规则

- 查看权和处置权分离：车辆跨辖区时可以允许查看，但处置需临时授权；
- 直控权限独立配置，不随值班长、管理员或系统管理员角色自动继承；
- 高风险操作要求强认证，必要时双人复核；
- 临时授权必须包含原因、生效和失效时间；
- 主体单位用户仅可查看本单位车辆和协同事项；
- 导出、证据调取、权限变更和配置发布全部审计；
- 权限不足显示原因和申请路径，不只隐藏按钮；
- 前端权限仅用于交互提示，服务端必须重新鉴权。

### 9.3 账号与设备

平台统一提供：

- 公安统一认证或项目身份源接入；
- MFA/数字证书能力；
- 登录设备与会话查看；
- 单设备下线和全部下线；
- 异常登录提醒；
- 密码策略或统一身份源跳转；
- 账号冻结、解冻、离岗回收和授权到期。

### 10.1 基本规则

- 平台服务端按现有移动端调用意图冻结兼容API、事件和错误码；本期不修改移动端源码、调用层或页面业务状态语义；
- REST 用于查询和命令提交，WebSocket/SSE 用于实时变化通知；
- 所有写操作携带 `clientRequestId`；
- 状态敏感操作携带 `expectedVersion`；
- 服务端返回 `correlationId`；
- 写接口只返回已受理事实，不提前承诺最终执行结果；
- 长流程使用回调与定时对账双通道；
- 实时断线后按 cursor 拉取增量，不依赖全量刷新；
- 前后端枚举、Schema 和错误码由统一契约生成。

### 10.2 统一响应

```json
{
  "code": "COMMAND_CONFLICT",
  "message": "车辆存在在途指令",
  "retryable": false,
  "correlationId": "CORR-20260912-000001",
  "currentStateVersion": 18,
  "data": null
}
```

HTTP状态与业务错误码必须同时正确：权限不足使用403，资源不存在使用404，版本/在途冲突使用409，字段或前置条件不满足使用422，外部依赖或网关异常使用502/504；不得以HTTP 200包装所有失败。错误响应不泄露网关地址、令牌、堆栈或主体单位敏感信息。

平台直控兼容投影规则（供未来外部接入使用，本期不改移动端）：

- 网关明确受理：返回移动端现有 `accepted`；
- 网关明确拒绝：返回移动端现有 `rejected`；
- 网关超时：向移动端返回现有错误响应，不新增业务状态；平台内部保留 `transport=timeout, businessResult=null, safetyHold=true, verification=pending`；
- 同一 `clientRequestId` 重试时，服务端返回已知最终结果；仍待核实时继续返回错误且不得重复调用网关；
- 核实确认目标动作已执行后，平台按急停/恢复分别映射到移动端已经存在的 `stop_requested` 或 `ready_for_stop`；确认未执行则恢复调用前投影；无法核实时继续返回现有错误并保持技术挂起；
- 迟到网关响应以同一 `clientRequestId/attemptId` 关联为核实证据，不得直接越过核实事项覆盖当前投影。

### 10.5 前后端交互约束

- 普通指令接口在指令、任务和outbox事务提交后返回HTTP `201`及 `commandId/taskId`，状态仍为“发送中/待接收”；这只证明平台已创建业务记录，不代表主体单位已经受理；
- 区域任务批次、配置发布和导出等需要后台处理的长流程返回HTTP `202`、资源ID/操作ID和查询位置；前端显示“平台已受理处理”，不得提前显示“已完成”；
- 网络重试必须复用同一 `clientRequestId`；只有明确允许重试且原请求已确认终态时，用户再次发起才生成新请求号；
- 任何状态推进都由服务端状态机完成，前端乐观更新只可用于非事实性的展开、收藏等界面状态；
- 查询列表使用稳定排序和cursor分页；实时事件断线重连后从最后cursor补齐，补齐完成前显示“正在同步”；
- 时间按ISO 8601传输并带时区，服务端保存统一时间基准；页面按项目时区显示，并同时保留设备时间和服务端时间；
- 文件先创建上传会话，再上传对象并提交业务引用；校验格式、大小、摘要、恶意内容和访问权限，禁止在业务JSON中直接传大文件；
- 错误码保持稳定并包含 `retryable/correlationId/currentStateVersion`；用户文案可本地化，但不得仅凭中文文案判断业务分支；
- `availableActions` 只用于提升体验，不构成授权凭证；服务端每次写入都重新校验身份、数据范围、动作权限、状态版本和安全锁；
- 迟到回调、重复回调和乱序事件按 `messageId/sequence/stateVersion` 幂等处理，原始报文与丢弃原因均可审计；
- 未来若项目方另行批准移动端外部接入，适配层与平台Web端必须共享领域服务；本期不建设移动端适配代码，不允许为兼容页面而各自维护另一套任务、告警或直控状态机。

### 10.6 跨端数据联动契约

本节是平台端提供的未来联调契约，不代表本期已修改移动端或已形成运行时联动。当前移动端源码继续使用localStorage/MockWS；本期平台只实现服务端事实、兼容API、事件、错误码和测试夹具。

```text
移动端现有页面（未来外部接入）/平台Web
        ↓ 版本化API、同一clientRequestId
API网关/BFF/平台兼容服务
        ↓ 同一鉴权、同一领域命令
指令任务/直控/告警事件/反馈等领域服务
        ↓ 同一事务保存事实 + Outbox
主体单位接口/直控网关/消息渠道
        ↓ 回调 + 主动查询对账
领域事件 → 平台读模型、未来移动端投影、工作台和通知
```

跨端一致性规则：

1. 同一业务事实只有一个 `commandId/taskId/alertId/incidentId/feedbackId`；未来移动端和平台端不得复制生成另一条记录；本期平台端先完成唯一约束和契约测试；
2. 未来外部接入时首次进入拉取服务端快照，实时事件按cursor增量同步；本期平台先实现快照、事件、cursor和重放接口；
3. 当前移动端localStorage/Mock仅属于现有演示运行，本期不改、不迁、不与平台生产库双写；未来接入必须另立项目并通过服务端事实源验收；
4. 平台发起普通指令后，未来移动端应通过原有任务列表看到同一`taskId`；本期只验证平台端指令—任务一致性及兼容Schema，不宣称移动端已看到；
5. 平台归档告警后，未来移动端应同步既有`resolved`；本期验证平台服务端自动归档条件和事件，不验证移动端运行时消费；
6. 平台完成直控核实后发布`direct-control.changed`；本期验证事件和投影Schema，未来移动端接入时只更新已有`ready_for_stop/stop_requested`投影；
7. 重复请求返回原业务ID和已知结果，迟到/乱序事件按 `messageId/sequence/stateVersion` 去重；服务端时间为排序和SLA计算基准，设备时间保留用于证据；
8. 平台独有的授权快照、技术挂起、复核、分派、通知投递、系统故障和配置发布字段不得转换为移动端新业务状态；未来接入时只转换为移动端已有的可执行、禁用或错误表现。

### 10.7 后台逻辑架构与部署建议

逻辑域按职责拆分为：统一身份与权限、主数据与车辆标识、车辆遥测、普通指令与任务、直控安全、告警与事件、反馈与证据、工作台与通知、配置治理、集成适配、审计与运维。页面只访问API/BFF，不得直接连接数据库、主体单位接口或直控网关。

首期推荐“模块化单体领域服务+独立异步Worker”的工程形态：业务模块边界、数据表归属、状态机和事件契约先逻辑隔离；普通指令与任务保持同一事务边界，使用outbox可靠投递；遥测、文件、缓存和消息分别使用适配其负载的存储。只有当容量、故障隔离、发布频率或团队边界出现实测证据时，再把高负载遥测、外部集成、通知或审计拆为独立服务，避免首期微服务化增加分布式事务和运维复杂度。

直控安全模块必须与普通业务权限和凭证隔离，单独管理网关密钥、强认证、授权快照、安全锁、核实队列和审计。任何模块故障均不得绕开领域服务直接补写终态；补偿任务只能基于原始请求、回调和对账证据推进状态。

### 10.8 契约交付基线

- HTTP契约使用[OpenAPI 3.1.2](https://spec.openapis.org/oas/v3.1.2.html)作为首期机器可读基线；其工具兼容成熟，后续升级到官方更新版本必须先通过代码生成、网关和契约测试验证；
- 事件契约使用[AsyncAPI 3.0.0](https://www.asyncapi.com/docs/reference/specification/v3.0.0)；每个事件声明发布者、消费者、幂等键、顺序键、Schema版本、兼容策略和示例；
- Schema采用“向后兼容增加”为默认策略：新增可选字段允许，删除/改名/改变枚举语义必须发布新版本；
- 每个写接口至少提供成功、幂等重放、403、409、422、502/504和未知结果示例；直控接口额外覆盖迟到回执和核实结论；
- CI必须执行Schema校验、破坏性变更检测、服务端契约测试、移动端兼容Schema测试和平台端生成类型检查；任一失败不得合并发布；本期不运行要求修改移动端源码的适配测试；
- 契约文件、错误码表、字典版本、状态机图和Mock场景使用同一仓库版本标签，禁止通过聊天或表格单独维护另一份口径。

当前官方[OpenAPI最新规范为3.2.0](https://spec.openapis.org/oas/latest.html)；本项目首期选择3.1.2是基于工具链兼容性的工程决策，不代表忽略新规范。待网关、代码生成器和测试工具完整支持后，再通过基线变更升级。

### 10.9 公共字段字典

| 字段 | 类型/规则 | 统一语义 |
|---|---|---|
| `*Id` | 服务端生成的非空字符串；全局或项目隔离范围内唯一 | 客户端必须视为不透明值，不从编号解析日期、辖区或权限 |
| `displayNo` | 可选的人类可读编号 | 仅展示和检索，不作为关联主键；编号规则变化不影响关系 |
| `clientRequestId` | 客户端每次逻辑写操作生成并在重试时复用 | 幂等键；同一调用方、接口和请求号只产生一次业务效果 |
| `correlationId` | 服务端入口生成/透传 | 串联API、领域事件、外部调用、回调、补偿和审计 |
| `stateVersion` | 单调递增整数 | 乐观锁和乱序判断；客户端写入使用 `expectedVersion` |
| `schemaVersion` | 契约版本字符串 | 决定字段结构；与业务状态版本分离 |
| `dictionaryVersion` | 字典版本字符串 | 决定枚举中文名称、颜色和可用范围，历史记录保留原版本 |
| `createdAt/updatedAt/serverAt` | ISO 8601 UTC时间，精确到毫秒 | 服务端权威时间；页面按Asia/Shanghai显示 |
| `deviceAt/sourceAt` | ISO 8601带时区，可为空 | 上游/设备时间，必须和服务端时间同时保留并计算漂移 |
| `cursor` | 服务端生成的不透明字符串 | 表示稳定分页或增量位置；客户端不得自行拼装 |
| `reasonCode/reasonText` | 稳定英文码+可本地化文字 | 程序只按码分支；文字用于用户理解，原始外部原因另存 |
| `availableActions` | 动作码、是否可用、阻断原因、当前版本 | 只优化界面；服务端提交时仍重新鉴权和校验 |
| `quality/freshness` | 质量枚举、数据时间、服务端接收时间、过期原因 | `unknown`、`stale`、`invalid` 与正常零值严格区分 |
| `evidenceRefs` | Evidence ID数组 | 只引用已完成上传和摘要校验的材料，不内嵌大文件或临时URL |

列表默认每页50条、最大200条，使用稳定排序+cursor；导出不复用超大分页接口。所有可选字段必须在Schema中明确“可缺失”或“可为null”，不得让不同客户端自行猜测空值语义。

## 11. UI/UE 规范

### 11.1 规范对照与采用结论

本项目不是面向公众的普通政务办事门户，也不是展示型数据大屏，而是面向值班民警和值班长的高风险、高频、长时间运行作业平台。因此，大厂规范用于统一组件、降低学习成本和提升工程质量；涉及直控、权限、超时、证据和审计时，以交警作业安全与可追溯要求优先。

| 参照体系 | 可借鉴能力 | 本项目采用方式 | 不直接照搬的部分 |
|---|---|---|---|

采用结论：后台Web首期正式选用 **React + TypeScript + Ant Design 6** 作为唯一桌面组件基线，通过本项目 Design Token 和业务组件层统一封装；不得同时拼接 TDesign、Arco 或移动端Tailwind页面样式。选择依据是其官方React实现、企业级复杂系统组件覆盖、类型能力和主题定制能力。移动端继续保持现有Vite/Tailwind实现，两端只共享业务字典、Schema和语义令牌，不共享页面组件。

浏览器基线按Ant Design官方兼容范围覆盖Chrome、Edge等现代浏览器最近两个大版本；信创浏览器不作名称猜测，纳入12.2兼容清单门禁，必须用建设方实际指定版本完成登录、表格、地图、文件、SSE/WebSocket和高风险确认回归。

### 11.2 视觉与设计令牌

- 延续移动端政务蓝，但平台端降低大面积高饱和蓝色使用；
- 操作区、数据区和风险区通过层级、留白和语义色区分；
- 同一状态在移动端、平台端和报表中使用相同名称和颜色；
- 车牌、VIN、车辆编号、时间、里程和统计数字使用等宽数字；
- 图标使用统一图标库，不使用 Emoji 作为正式业务图标；
- 不依赖颜色单独表达成功、警告或失败。

建立项目级令牌，禁止在页面中写死同义样式：

- 以4px为最小单位、8px为主要间距节奏；页面边距24px，卡片内边距16—24px，按信息密度统一选档；
- 正文默认14px，辅助信息12px，区块标题16px，页面标题20—24px；正文行高不低于字号的1.5倍；
- 常规控件高度32px，关键表单和触控兼容场景使用40px；表格支持紧凑40px和标准48px两档行高；
- 圆角、阴影和描边保持克制，主要依靠层级、留白和边界组织信息，不使用大面积渐变、发光和装饰性玻璃效果；
- 红色仅用于急停、严重风险和不可逆警示；橙色用于待处理风险；蓝色用于进行中；绿色用于已完成；灰色用于失效或不可用，并同时配文字/图标；
- 时间默认显示绝对时间，必要时附相对时长；车辆状态必须同时显示数据产生时间和新鲜度。

### 11.3 桌面端布局

- 设计基准：1440px，最低支持1280px；
- 主导航保持稳定，页面级操作靠近标题区；
- 查询表默认展示4个高频条件，其余折叠；
- 表格首列和操作列可冻结，支持列设置、密度、导出和分页；
- 监控页优先保证地图与车辆状态，操作面板不得遮挡关键地图区域；
- 详情优先使用抽屉，复杂档案使用独立详情页；
- 工作台优先展示需要处理的事项，而不是只展示统计图。

平台默认采用浅色作业界面以保证长时间阅读和表格清晰度；大屏或夜间值守可提供独立深色主题，但两套主题必须使用同一语义令牌并分别通过对比度与状态辨识测试。监控作业页可高密度，配置与高风险操作页不得为追求密度压缩确认信息。

### 11.4 状态反馈

所有页面必须提供：

- 加载中；
- 空数据；
- 搜索无结果；
- 接口异常；
- 数据过期；
- 权限不足；
- 无法核验；
- 部分成功；
- 断线重连；
- 提交中和防重复提交。

“无法核验”必须同时展示原因，例如数据未接入、接口异常、权限不足、规则缺失或数据已过期。

### 11.5 高风险交互

直控、撤回、归档、配置发布、批量操作和权限变更的确认框至少显示：

- 操作对象；
- 当前状态；
- 影响范围；
- 操作后果；
- 是否可撤销；
- 操作依据或备注；
- 强认证/复核状态。

文案必须区分“已提交”“已送达”“已受理”“执行中”“执行完成”，不得用“操作成功”笼统覆盖不同阶段。

### 11.6 可用性与无障碍

- 支持键盘操作、焦点态和可读的表格行操作；
- 关键文字满足WCAG AA对比度；
- 桌面端高频图标按钮有效点击区建议不小于32×32px，触控兼容和安全关键动作不小于44×44px；
- 风险图标同时带文字；
- 表单错误定位到具体字段并保留已填内容；
- 监控页面支持高密度模式，但不得牺牲状态识别和误操作防护。

## 12. 非功能与运行要求

以下值作为研发、环境建设和首轮压测的默认基线；合同或正式制度更严格时取更严格值。真实清单改变容量数值时，只更新参数，不改变业务架构。

| 指标 | 默认研发基线 | 冻结与验收方法 |
|---|---|---|
| 首期车辆规模 `N_prod` | 以准入/城市平台在上线范围内的去重有效 `vehicleId` 数为准 | 阶段0导出车辆清单、摘要和统计时间；演示种子不得计入 |
| 设计容量 `N_cap` | `max(2 × N_prod, N_prod + 已书面确认的24个月新增量)` | 以该容量完成数据模型、缓存、消息和存储估算；合同明确更高值时覆盖 |
| 峰值在线客户端 `C_peak` | `ceil(1.2 × (同班PC席位+移动端在线用户+大屏/系统会话))`，各项按真实清单代入 | 身份源、班次和大屏清单去重；压测保持权限分布和真实查询比例 |
| 峰值遥测吞吐 | `1.2 × N_cap × 单车峰值上报频率` | 不凭页面刷新频率估算；使用数据源协议的峰值频率和真实消息大小 |
| 普通查询 | P95≤2秒、P99≤5秒 | 不含离线统计和文件导出；按真实权限、分页和索引压测 |
| 普通指令建档 | 平台本地事务P95≤1秒返回201及 `commandId/taskId` | 不把主体单位受理时间计入本地建档；外部阶段单独监控 |
| 实时状态推送 | 服务端收到有效变化至客户端可见P95≤2秒 | 页面显示数据时间；断线补偿期间显示“正在同步” |
| 断线数据收敛 | 网络恢复后60秒内完成有权范围内的增量补齐 | 超出后创建同步异常，不能静默保持旧状态 |
| 可用性 | 核心业务服务月度99.9%，外部依赖单独计量 | 计划维护窗口是否剔除由合同冻结；不得用外部故障掩盖本平台故障 |
| 恢复能力 | 核心服务RTO≤2小时、核心数据库RPO≤5分钟 | 指令、任务、直控尝试、outbox和审计在正常事务内不得有意丢失；按灾备演练核验 |
| 稳定性测试 | 峰值负载连续30分钟，70%峰值负载连续8小时 | 无数据错序、重复终态、内存持续增长和不可恢复积压 |
| 直控接口 | 仍按移动端现有 `accepted/rejected`；技术超时进入挂起核实 | 网关SLA单独记录，不以浏览器超时替代网关业务结果 |

### 13.4 直控合规与责任边界

现行公开试点和运输安全指引将安全保障责任落实到车辆生产企业、使用主体、运营主体及其安全管理体系；因此，“交警平台可直接控制任何无人车”不能作为全国通用默认权限，只能以属地法律政策、项目职责、道路测试/示范/运营条件、主体单位责任协议和车端能力共同证明。每个生产直控动作必须保存当时有效的授权、范围、车辆、动作、操作者和能力快照，任一条件缺失即阻断。

道路交通安全法自动驾驶相关修改在本稿日期仍处于草案审议进程，不能作为已经生效的直接授权条款。项目法制人员应在上线评审和每次政策版本变化时复核适用性。

### 14.6 风险登记与控制

| 风险 | 触发条件与影响 | 控制措施 | 剩余风险/验收证据 |
|---|---|---|---|
| 指令、任务和外发消息部分写入 | 任一环节失败会出现有指令无任务、移动端无待办或重复外发 | `Command(sending)+Task(pending_receipt)+Outbox` 同事务写入，事务提交后异步投递并持续对账 | 以注入数据库/消息/接口故障后无孤儿记录、恢复后只投递一次验收 |
| “移动端完全不改代码”被误解为本期已实现跨端联动 | 当前localStorage/Mock与平台服务端天然是两套事实，不能从平台单方开发推导运行时一致 | 冻结“本期只开发平台端；兼容API/事件作为未来外部接入契约；不修改移动端源码”的边界 | 当前阶段只验收平台自洽和兼容Schema；跨端运行时联动须另立项目并取得批准 |
| 生产接口失败时自动回落Mock/localStorage | 页面看似可用但产生虚假车辆、任务和完成状态，污染真实审计 | 生产构建禁用Mock回落；接口失败只显示异常/过期/无法核验，本地仅保留草稿和界面偏好 | 断网和依赖故障测试中不得产生任何Mock业务事实 |
| 主体单位接口语义不一致 | “送达、受理、执行、完成”混用，产生虚假闭环 | 契约测试、原因码映射、回调+主动对账、原始报文留存 | 仍可能受外部系统可用性影响；以异常演练和对账差异闭环验收 |
| 直控超时结果不确定 | 重试可能造成重复动作，直接判拒绝又可能错误解锁 | 技术状态与业务结果分离，开启 `safetyHold`，禁止重复调用，双人核实后映射现有移动端状态 | 核实期间车辆真实状态仍可能未知；以超时、迟到回执和人工核实演练验收 |
| 直控授权或责任边界不成立 | 技术接口可调用但无属地/项目授权，造成越权和责任争议 | 生产启用门禁、逐次授权快照、强认证、动作范围校验、过期自动失效；管理员不默认继承直控 | 法制和责任单位书面确认、权限穿透测试、快照抽查和应急停用演练 |
| 本地历史数据迁移重复或丢失 | 同一指令/任务被重复导入，旧字典无法解释 | 迁移映射表、业务ID去重、幂等导入、原值留存、迁移前后对账和可回滚批次 | 无稳定ID的数据只能标“来源不完整”；以抽样追溯和全量计数对账验收 |
| 状态投影漂移 | 移动端、平台端和主体单位显示不同状态 | 服务端状态机唯一写入、字典版本、事件序列和cursor补偿；客户端只保存缓存投影 | 断网期间存在短暂延迟；以恢复后自动收敛和差异告警验收 |
| 遥测过期或乱序造成误操作 | 旧位置/旧速度被当成当前事实 | 同时保存设备时间和服务端时间，校验序列、新鲜度和质量，过期时阻断相关动作 | 数据源持续异常时只能人工处置；以乱序、跳点、时钟漂移用例验收 |
| 合规功能范围膨胀 | 把试点、草案或外部系统能力默认写成一期承诺 | 条件模块必须绑定政策层级、条款、职责、数据源、合同和验收场景 | 属地政策变化仍需版本化复核；以政策适用性表和变更记录验收 |
| 工程默认值被误写成合同/法定要求 | 造成不必要成本、错误验收或合规争议 | 参数记录来源、类型和覆盖优先级；正式制度/合同更严格时变更基线，页面不显示“法定”文案 | 评审逐项核对12章参数来源和批准记录 |
| 统一认证或权限治理未落地 | 共享账号、离岗权限、管理员继承直控导致越权 | 统一身份、MFA、功能/数据/动作三层授权、临时授权到期和全量审计 | 身份源故障时禁止降级为匿名高权限；以越权和离岗回收测试验收 |

风险关闭原则：风险只有在责任人、措施、验收证据和剩余风险均明确后才可降级；不得以“接口已通”“页面已展示”或“演示成功”替代业务和安全验收。

## 15. 验收与质量核验

### 15.1 业务验收

| 场景 | 验收重点 |
|---|---|
| 告警响应 | 响应、分派、指令/任务关联、归档前置条件 |
| 普通指令 | 指令+任务+outbox原子创建、幂等、回执、失败分类、撤回限制、超时、人工兜底 |
| 直控 | 逐次授权快照、独立权限、强认证、并发互斥、超时技术挂起、不同人员复核、移动端现有状态同步 |
| 区域任务 | 逐车预检、部分成功、失败原因、不整体回滚 |
| 现场反馈 | 多次追加、原始材料、平台核验标记独立存储、不可覆盖 |
| 非成功反馈跟进 | 部分/失败反馈生成或维持唯一WorkItem，具备负责人、下一动作、`dueAt/dueAtSource`；逾期升级且在个人/值班长工作台可见；只有风险解除或后续事项明确承接后才能关闭 |
| 值班交接 | 单席模式验证收班快照、导出和续办；多席模式验证认领、分派、升级、双签和临时权限到期；切换模式不丢在途事项 |
| 数据异常 | 旧编号、乱序、重复、缺失、时钟漂移 |
| 权限 | 越权查询、越权操作、临时授权、离岗回收 |

### 15.2 架构验收

- 页面不得直接调用主体单位或直控网关；
- 指令、任务、告警、事件只由对应服务推进主状态；
- outbox、幂等、版本锁、回调对账和cursor补偿有效；
- 前后端枚举由契约生成，禁止维护两套字典；
- 读模型可重建，事实记录不可被统计或页面逻辑覆盖；
- 外部系统不可用时有明确降级和人工兜底。
- 历史静态演示页不进入生产构建、正式路由或契约验收；P04/P05必须使用统一Schema和服务端查询。

### 15.2.1 平台兼容契约验收（本期范围）

- 移动端源码、依赖、构建配置、页面、交互和localStorage/Mock调用均无修改；
- 平台服务端为监控、单车指令、急停/恢复、任务、告警、事件和反馈提供兼容API、事件、错误码和测试夹具；
- 平台服务端以唯一业务ID、状态版本、权限和安全锁裁决平台Web写入；
- 兼容Schema不新增移动端告警类型、任务状态、事件类型或直控业务结果；
- 使用模拟调用方完成契约、幂等、版本冲突、超时、迟到事件和错误码测试；
- 验收结论只写“平台兼容契约通过”，不得写“现有移动端已经与平台联动”。

### 15.2.2 未来跨端一致性验收矩阵（后续外部接入，不属于本期代码范围）

| 用例 | 预期业务事实 | 两端表现与核验证据 |
|---|---|---|
| 移动端下发普通指令 | 同事务生成唯一 `commandId/taskId/outbox messageId` | 平台立即看到发送中指令和待接收任务；数据库故障回滚时三者均不产生 |
| 平台下发普通指令 | 生成同一指令和任务事实 | 移动端原任务列表出现同一 `taskId`、既有状态和一致车辆信息 |
| 主体单位回调受理/执行/失败 | 服务端状态机只推进一次 | 移动端与平台最终状态一致；重复、乱序回调有丢弃原因和审计 |
| 移动端追加现场反馈 | 每次产生新的 `feedbackId/version` | 平台时间线可见且原记录不可覆盖；内部核验不改变移动端任务主状态 |
| 成功任务联动告警 | 仅 `completed + success feedback` 自动归档 | 两端同步到既有已归档/`resolved`；部分、失败、异常或撤回不误归档 |
| 直控网关明确受理/拒绝 | 记录唯一尝试和原始响应 | 移动端仍显示现有二态结果；平台展示授权快照和技术明细 |
| 直控超时后核实已执行 | 先保持 `safetyHold`，双人核实后推进投影 | 移动端在事件/进入页面/恢复/重连时收敛到既有目标意图状态，不出现新枚举 |
| 直控超时且无法核实 | 不产生伪终态，不重复调用网关 | 移动端收到现有错误；平台保持挂起、负责人和下一步升级动作 |
| 应急事件不创建区域任务 | 只生成事件 | 两端事件可查，任务数为0，事件人工闭环不修改其他任务 |

| 同一请求重复提交 | 返回原业务ID和已知结果 | 不出现重复指令、任务、反馈或网关调用 |
| 离线、切后台、重登和断线重连 | 本地不产生业务终态，恢复后按cursor补齐 | 补齐完成后两端版本一致；差异自动产生数据质量待办 |

### 16.2 关键偏差与本版修正

| 原规划/常见做法偏差 | 现实风险 | 本版修正 | 落地核验 |

| 普通指令等待主体单位受理后才创建任务 | 发送中阶段移动端无待办，接口超时还会出现有指令无任务 | 预检后同事务创建 `Command(sending)+Task(pending_receipt)+Outbox`，再异步外发 | 故障注入验证同生同回滚、恢复后只外发一次 |

### 16.3 定版结论

本方案已经形成专业的平台侧总体设计。以下内容已作为开发基线冻结：

1. 直控保持移动端现有二态结果和三种意图状态；平台内部增加与急停业务意图分离的技术挂起 `safetyHold`；
2. 平台作为既有城市级平台下的交警业务域建设；
3. `vehicleId` 为唯一主键，车牌、车辆编号、设备ID和二维码为外部标识；
4. 查看权与处置权分离，跨区处置采用有时效的临时授权；
5. 普通指令、直控、任务、告警、事件和反馈沿用移动端状态与边界；
6. 普通指令预检后由服务端原子生成发送中指令、待接收任务和outbox，平台端严格对齐移动端当前逻辑；
7. 本期移动端源码、依赖、构建、页面、交互和数据访问均不修改；平台提供未来可接入的兼容API、事件和投影Schema，但当前移动端运行时数据联动不计入本期完成范围；
8. 直控生产启用必须具备属地/项目授权、责任协议、车辆能力、网关联调和逐次授权快照；核实结果只映射为移动端既有状态；
9. 合规取证、企业门户、DSSAD、OTA、仿真等属于条件型扩展，不阻塞核心平台开发；
10. 当前二态直控不仅是页面约定，也是现有数据迁移和回归脚本的守护条件；任何未来三态提案必须先形成获批业务变更，再同步修改契约、迁移规则、平台投影和测试，禁止单点翻案；
11. 既有`交警指挥指令日志.html`定性为历史静态演示页，不作为后台正式路由、数据契约或交付完成证据；
12. 非成功反馈必须由WorkItem承接责任人、下一动作和到期时间；值班协同按实际运行模式启用，不按人数阈值硬裁剪。

产品方案侧已无影响主流程的开放决策。项目方只需按I-01至I-10提供真实清单和书面依据：车辆/主体单位/辖区、组织班次、统一身份、普通指令接口、直控授权和网关、遥测地图、信创环境、数据制度及合同SLA。提供前按12章默认值和降级规则开发；提供后只代入参数、完成联调和生产放行，不重新定义移动端或后台业务逻辑。
