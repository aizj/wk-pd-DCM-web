## 1. 审查范围与判定方法

### 1.1 审查基线

| 层次 | 文件 | 本次用途 |
|---|---|---|
| 领域详细设计 | `V0.4 FR-1 服务产品与数据授权功能详细规格` | 审查业务对象、状态分离、授权链、能力与权益规则 |
| 研发分层规格 | `V0.5 FR-1 四层需求规格` | 审查用户故事、产品需求、后端需求、页面交付的追溯闭环 |
| 产品说明书 | `V0.6 数据上车服务运营平台产品说明书` | 审查全产品范围、信息架构、页面、状态、路线图与实施顺序 |

V0.1～V0.3 仍是产品全景、功能深化和合理性审查输入，但不能替代 V0.8 FR-2 及后续 FR-3～FR-5 的研发级规格。

### 1.2 判定规则

| 判定 | 含义 |
|---|---|
| GO | 输入、责任人、验收和依赖足以启动该范围工作 |
| Conditional Go | 可在明确边界内启动；每个故事或模块仍需单独通过 DoR |
| NO-GO | 开工将导致范围、状态、权限、接口或验收由研发临场决定 |
| PASS | 已有稳定且可追溯的文档基线 |
| PARTIAL | 方向已定义，但缺实例、契约、签认或执行证据 |
| BLOCKED | 缺口会直接导致错误实现、返工、越权或无法验收 |

审查遵循第一性原理：只有当“对象、状态、动作、权限、契约、证据、失败出口”可以被同一组可复现实例验证时，才视为可开发；页面存在、接口返回 200 或消息到达网关，都不能单独证明业务闭环成立。

## 4. P0 研发阻断项

### B01 FR-3～FR-5 四层草案待评审冻结（原文档缺口已关闭）

- **现状**：FR-2 已由 V0.8 补齐用户故事、产品功能需求、常规研发需求、页面研发清单、追溯矩阵和 DoR；FR-3 参数配置、FR-4 测试发布运行、FR-5 证据与退出各有 V0.1 四层评审稿，但对象/状态/原因码、接口及目标故事的联合评审未完成。
- **风险**：业务规则、状态机、后台任务、前后端边界和验收责任会在开发过程中临场决定。
- **关闭证据**：FR-2～FR-5 独立四层规格、追溯矩阵、DoR/DoD、异常与权限验收经产品、架构、研发、测试、OEM/领域 Owner 签认，目标故事通过 DevelopmentStartDecision。
- **门禁**：FR-2～FR-5 不再因“无四层草案”被阻断，但仍受 B02～B10 和逐故事门禁约束；FR-3～FR-5 评审冻结前继续阻断对应业务模块正式编码。

### B02 M0 决策项尚未签认

- **现状**：主体身份、标准 Profile、治理等级、首批服务、OEM 能力模板、质量阈值、审批矩阵、FR 接口、SLA/RTO/RPO 等已有待决清单，但缺最终结论、Owner、截止日期和签认记录。
- **风险**：研发把建议值写成项目事实，后续产生大范围返工或越权。
- **关闭证据**：M0 决策表中每项具有 `DECIDED / DEFERRED / REJECTED` 结论、依据、责任人、生效日和影响范围。
- **门禁**：阻断依赖该决策的业务规则冻结和生产验收。

### B03 S1 实例未冻结

- **现状**：建议从信号灯提醒或 GLOSA 选择一个服务，但尚未锁定服务版本、OEM、应用、车型、区域、环境、通道、数据源、审批人和证据等级。
- **风险**：只能开发通用空壳，无法构造贯穿全链的真实 fixture。
- **关闭证据**：一条完整、匿名化也可复现的 S1 对象链及其固定 ID、Revision、状态和期望结果。
- **门禁**：阻断 S1 业务联调和端到端验收。

### B04 S1 页面契约尚未全平台冻结（FR-2 文档级缺口已补齐）

- **现状**：FR-2 V0.8 已对 P01～P15 补齐页面范围、内容、交互、业务规则和验收，并建立高风险字段字典、动作—权限矩阵及逐页六态差异。FR-3～FR-5 V0.1 已有页面级验收草案，但真实 S1 对象值、UX 定稿、动作权限、逐页六态、ViewModel/API 映射、原因码字典和验收 fixture 未签认。
- **风险**：UX、前端、后端和测试对同一字段及按钮形成不同理解。
- **关闭证据**：S1 页面完成字段矩阵、动作矩阵、RBAC/ABAC 矩阵、Loading/Empty/Error/Partial/No Permission/Conflict 六态与 Given/When/Then。
- **门禁**：FR-2 不再因“页面规格缺失”被阻断，但在 S1 值、契约和验收证据签认前，仍阻断相应业务页面定稿和正式编码。

### B05 状态机与原因码尚未成为全平台单一事实源

- **现状**：FR-2 V0.8 已分离 17 类状态对象/维度（含影响快照 status 与 validity 两个正交维度），在 FR2-RD-02 给出初始可达、合法迁移、守卫、Owner、副作用与迟到事件规则。但 StateDictionaryVersion / ReasonCodeVersion 尚未形成可被 API、事件、前端、Mock 和自动化测试共享的版本化产物，FR-1 及 FR-3～FR-5 仍需统一。
- **风险**：页面、数据库、事件、日志和测试使用不同状态，形成“显示成功但实际未生效”。
- **关闭证据**：统一状态／原因码仓库及版本，所有需求、接口、前端枚举和测试从同一来源生成或校验。
- **门禁**：FR-2 状态语义可进入联合评审与 Schema 设计；版本化字典、原因码和契约测试未通过前，仍阻断状态相关核心编码和联调。

### B06 API、事件与 Mock 契约未冻结

- **现状**：已有对象与架构原则，但缺正式请求/响应、分页、过滤、排序、幂等、ETag/Revision、错误码、异步任务、回调/事件、上传下载和鉴权错误契约。
- **风险**：前后端并行开发不可控，外部 OEM、区域云、边缘云和网关难以联调。
- **关闭证据**：可校验的 OpenAPI/AsyncAPI、Mock Server、ViewModel、完整 fixture 和契约测试。
- **门禁**：阻断业务前后端并行编码与外部联调。

### B07 路由、子页与跨页上下文未完全冻结

- **现状**：工作区、菜单和页面 ID 已有，FR-2 V0.8 已对 P01～P15 补充主要深链、返回上下文和 Revision 语境；但完整 routeName、URL 参数 Schema、浏览器前进/后退、异常出口及跨 FR 返回契约仍未签认。

- **关闭证据**：需求—用例—fixture—环境—证据追溯矩阵，覆盖正常、异常、越权、跨租户、并发、重复、迟到、到期、撤销和依赖失效。

### B09 技术与非功能基线未签认

- **现状**：V0.6 给出推荐技术架构，但仓库、框架版本、浏览器矩阵、部署拓扑、可观测性、P95/P99、数据规模、RTO/RPO、留存和安全基线仍需项目确认。
- **风险**：研发先行假设被误认为项目约束，后续迁移成本高。
- **关闭证据**：ADR、NFR 基线、容量模型、部署图、安全设计和运维责任表。
- **门禁**：可做可替换 Spike；阻断架构定版、性能验收和生产发布。

### B10 开发授权和代码边界需显式确认

- **现状**：当前文件是文档评审交付，不能自动推导出修改任意代码、移动端或 OEM 系统的权限。
- **风险**：范围漂移，误改不在本项目授权内的系统。
- **关闭证据**：明确仓库、分支、技术栈、部署环境、首批故事、Mock 边界、验收人，并书面确认“平台端开发；移动端、车端和 OEM 系统不改动”。

## 9. 文档口径与追溯规则

### 9.1 口径优先级

当文档表述冲突时，按以下顺序处理：

1. 已签认的 M0 决策、Project Profile、授权文件、ICD、DVP&R 和 DevelopmentStartDecision；

5. V0.4 的领域推理、对象定义和详细业务规则；
6. V0.1～V0.3 的方向性方案与评审建议。

### 9.2 需求追溯最小链

```text
Policy/Profile/Decision
  → JTBD/Outcome
  → UserStory
  → ProductRequirement
  → RDRequirement
  → Page/Action/API/Event/State
  → TestCase/Fixture
  → Release/Runtime/Evidence
```

每个 P0 需求至少要能双向追溯一次；孤立页面、孤立接口、孤立状态或孤立测试不得进入生产版本。

## 10. 评审会议建议顺序

1. **M0 决策评审**：只解决主体、标准、治理等级、S1、阈值、责任和接口边界；
2. **S1 故事地图评审**：冻结最小用户旅程、页面深度、对象实例和非目标；
3. **FR-2～FR-5 需求评审**：评审冻结 FR-2 V0.8，并依次评审、修订与签认 FR-3～FR-5 V0.1 四层草案；
4. **三方规格评审**：产品、研发、测试共同冻结字段、动作、权限、状态、API 和验收；
5. **架构与安全评审**：冻结 ADR、NFR、部署、安全、审计、DVP&R 和恢复策略；
6. **开发启动评审**：只对通过 DoR 的故事签发开发权限；
7. **迭代验收**：按业务终态和证据验收，不按页面数量或接口数量验收。

FR-2 订阅四层规格已由 V0.8 成稿，FR-3～FR-5 V0.1 草案也已形成；下一步应依次联合评审与冻结配置、测试发布、证据退出的对象/状态、接口与验收。每一层仍沿用“对象与状态先冻结、页面与接口后收敛”的顺序，避免页面先行导致对象与状态倒置。

## 12. 最终建议

1. **保留 0.4、0.5、0.6 的分工，不合并成一份巨型文档。** V0.4 负责领域深度，V0.5 负责 FR-1 研发分层，V0.6 负责全产品和页面全景，V0.7 负责开工治理。
2. **FR-2 已形成 V0.8 四层规格，下一份正式需求转入 FR-3。** 继续复用 `requirements-spec-generator` 的四层结构，完成“有效订阅→参数配置修订版→待验证配置”的产品与工程闭环。
3. **用一个 S1 实例驱动所有规格。** 同一组固定 ID 和 Revision 贯穿页面、API、事件、测试和证据，避免每份文档各举一套例子。
4. **建立单一事实源。** 状态、原因码、权限和字段枚举不得分别手写在前端、后端和测试中。
5. **按故事发放开工权限。** 不以整份说明书“评审通过”替代每条故事的 DoR。
6. **保持平台责任边界。** 平台直接控制的是服务资格、配置、发布和网关投递；车辆接收、HMI 展示和算法消费必须依赖相应回执和证据等级，不得推定。

**最终判断：文档体系已达到“可进入研发准备与分故事开工”的成熟度，但尚未达到“全平台业务功能无条件开工”的成熟度。先关闭 U01～U08 中与首批故事直接相关的项目，再启动对应编码，是当前风险最低且返工最少的路径。**
