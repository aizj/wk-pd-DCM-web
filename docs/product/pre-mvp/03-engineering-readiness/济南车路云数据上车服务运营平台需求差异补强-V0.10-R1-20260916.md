## 一、用户故事

### US-ADD-01 可信的订阅准入

作为 OEM 接入负责人，  
在为不同服务和车型申请接入时，  
我希望确认申请确实位于已获准的用途、区域、能力和期限内，  
以便在提交前消除越权和误判风险。

- AC1：在权益、服务、能力与范围均有效时，当我核对准入结果，用户应能够确认本次申请与可用权利逐项一致，并且结论可由双方复核。
- AC2：在范围不可确定、依据已变化或条件不满足时，当我继续办理，用户应能够得知具体差异和责任方，并且不会误以为申请已经通过。
- AC3：当我完成准入核对后，用户应能够将固定且当前有效的结论交给审批人员，并且对方能依据同一事实作出决定。

### US-ADD-02 可验证的补正

作为订阅运营负责人，  
在接入申请存在材料或依赖缺口时，  
我希望确认缺口已经得到独立核验且重新评估，  
以便只将真正消除风险的申请继续流转。

- AC1：在明确缺口、责任人和期限后，当相关方完成处理，用户应能够区分材料已提交、已核验和风险已解除，并且结果可追溯。
- AC2：在材料仍不充分、核验失败或依据变化时，当我再次核对，用户应能够看到未完成原因和下一动作，并且历史结论不被悄然改写。
- AC3：当风险得到重新评估后，用户应能够将最新结论继续用于审批，并且审批方能核对补正过程与独立责任。

### US-ADD-03 真实的恢复确认

作为服务运行负责人，  
在交通事件告警经过处置后，  
我希望凭可核验的恢复事实确认影响已经结束，  
以便避免只凭口头说明关闭仍在影响车辆服务的事件。

- AC1：在处置完成并经过约定观察时，当我确认恢复，用户应能够看到与影响范围相符的恢复依据和验证责任人。
- AC2：在仅有文字说明或部分目标仍异常时，当我尝试结束处置，用户应能够看见尚未核验的目标和后续责任，并且事件不被错误认定为已恢复。
- AC3：当所有必要目标得到有效核验或有权例外后，用户应能够将事件交接给运营复盘，并且保留完整证据。

## 二、产品功能需求

## 功能需求：FR-ADD-01 当前申请的准入检查

系统应提供基于本次申请和当前权利事实的准入检查能力，支持 OEM 接入负责人确认范围、期限及依赖有效性，避免跨服务复用结论。

关联用户故事：US-ADD-01。关联正式需求：V0.8 FR2-FR-03/04/05/06、FR2-RD-03/04；本条是验收补强，不改变正式枚举。

### 功能范围

- 创建新申请时分别校验主体、应用、服务/Offering、能力组、Coverage、通道和期限。
- 形成独立的“尚未检查—检查中—已形成结论”过程；固定结果可追溯其输入与规则版本。
- 基础事实发生变化后，显示原结论失效及重新检查入口。

### 关键信息

- 申请与权益的对象标识和版本、允许范围交集、检查运行状态、业务结论、有效性、规则差异、责任人与下一动作。

### 业务规则

- 新申请没有自己的当前检查结果时，不能称为通过；未知范围不等于全域。
- 条件通过必须有明确条件与责任，不可豁免的授权或安全阻断不能由条件通过覆盖。
- 只有当前输入、时效及检查结论满足准入要求，才允许正式提交。

### 验收标准

#### AC1：核心任务可完成

当申请绑定有效权益及已知范围时，用户完成检查后可取得本申请独立且可解释的结论。

#### AC2：关键信息完整

查看结论时，服务、能力、空间、期限及检查三维状态均可辨别，不复用别的服务的发现项。

#### AC3：主要规则有效

提交范围超出权益交集、已过期或身份不一致时，系统阻断提交并给出准确原因。

#### AC4：异常场景有反馈

依赖缺失或输入变化时，系统保留草稿、标注未知/失效，提供补正或重新检查路径。

#### AC5：结果可继续流转

只有当前有效且固定的检查结果才随不可变申请进入审批，历史检查可查。

## 功能需求：FR-ADD-02 补正与重新核验

系统应支持将发现的缺口交给责任人补正，区分材料登记、独立核验和重新检查，帮助订阅运营负责人决定申请能否继续。

关联用户故事：US-ADD-02。关联正式需求：V0.8 FR2-FR-05/06/07/13、FR2-RD-03、FR2-P06。

### 功能范围

- 将发现项转为有 Owner、期限、证据要求和复检条件的补正任务。
- 记录材料来源与验证结果；核验后重新检查并保留旧结果。
- 未完成项保持开放并呈现下一步。

### 关键信息

- 来源发现项、任务状态、材料引用、处理人、验证人、期限、新旧检查结果和失败原因。

### 业务规则

- “已登记材料”不是“已核验”；“复检请求已登记”不是“重新检查完成”。
- 处理人不得在要求独立核验的情况下自行判定其材料有效。
- 不得仅选择此前同一证据引用就声称新增材料已补齐。

### 验收标准

#### AC1：核心任务可完成

从有效缺口创建任务，责任人提交新材料后，独立验证人能给出核验结果。

#### AC2：关键信息完整

运营人员能区分任务进度、证据来源和检查结果，并追溯原发现项。

#### AC3：主要规则有效

权限、职责分离、材料版本与任务状态不满足时，补正不能被标为完成。

#### AC4：异常场景有反馈

证据不存在、过期或核验失败时，任务仍开放，并有原因、Owner 和下一动作。

#### AC5：结果可继续流转

补正核验后产生新的检查结果，仅当前有效且无硬阻断的结果允许继续审批。

## 功能需求：FR-ADD-03 运行事件恢复核验

系统应支持服务运行负责人在真实恢复事实基础上关闭事件，避免文本说明或单一回执造成虚假恢复。

关联用户故事：US-ADD-03。状态：FR-5 正式四层规格的待评审输入，未授权业务编码。

### 功能范围

- 关联受影响目标、处置动作和恢复证据。
- 展示核验人、观察时段、结果及仍未核验的目标。
- 区分处置完成、恢复确认和事件关闭。

### 关键信息

- Incident、WorkItem、影响范围、证据引用/类型/时点、验证身份、观察窗、异常目标及例外依据。

### 业务规则

- 备注文字、网关 ACK、意图回执均不能替代对应级别的恢复事实。
- 未完成的目标持续开放；部分恢复只记录部分结果，不聚合为全部恢复。
- 恢复与关闭权限由 M0 职责矩阵确定，必要时职责分离。

### 验收标准

#### AC1：核心任务可完成

有权人员在完整证据与观察结论齐备时，能够完成恢复核验。

#### AC2：关键信息完整

事件详情能展示每个目标的验证结果、采集时点、证据等级和责任人。

#### AC3：主要规则有效

仅有“已恢复”描述或部分目标成功时，不能将整体事件视为恢复。

#### AC4：异常场景有反馈

证据不可读、过期或外部确认未回时，保持待核验，并提示责任与补证路径。

#### AC5：结果可继续流转

核验结论和证据固定后可进入关闭与复盘，原始告警、处置与恢复事实分别保留。

## 三、常规研发需求

## 研发需求：RD-ADD-01 草稿输入固定与预检隔离

关联功能需求：FR-ADD-01。

### 需求描述

实现以结构化 ID/Revision 和租户/应用关系为输入的准入校验，不从显示摘要拆解能力，也不把已知 Coverage ID 当作范围内。新草稿创建时，系统应登记尚未检查的状态；检查服务按当前输入快照、规则集、时效创建独立 Run/Finding。提交时，应再次比较申请内容哈希、规则版本、有效性、权限和权益交集，失败时只返回有解释的阻断，不生成正式申请或审批对象。

### 数据与状态

| 对象 | 关键引用与处理 | 不变量 |
|---|---|---|
| DraftRequest | tenant、application、service/offering、capability、typed coverage、channel、`[validFrom,validTo)` | 创建草稿不附带任何其他申请的预检通过结果 |
| PrecheckRun/Finding | requestId、inputHash、ruleSetVersion、各层证据与 `runStatus/outcome/validity` | 新执行生成新 ID；旧 Run 不覆盖；变化后旧结果 STALE |
| RequestRevision | 固定输入、当前 Run、幂等键及 ETag | 提交只在同一快照当前有效时成功；正式 Revision 不变 |

### 验收标准

#### AC1：独立检查

新建信号灯和 VRU 两份不同服务草稿时，初始均无复用的通过结果；各自检查形成不同输入哈希、Run 与匹配服务的 Finding。

#### AC2：范围与期限

申请 Coverage ID 存在但不包含于权益允许范围，或 `validTo` 已早于当前时刻时，提交应被拒绝并返回对应原因码。

#### AC3：过期与冲突

输入或上游 Revision 变化后，旧 Run 只读且标为 STALE；相同幂等键不同 payload 或过期 ETag 不覆盖已有提交。

#### AC4：服务端守卫

跨租户、错误 ApplicationClient、未知能力版本和未经启用的通道均在服务端被拒绝；前端隐藏不替代守卫。

#### AC5：审计与后续流转

成功提交时能追溯同一快照、检查结论、审批 Case 与审计关联；失败不生成半提交对象。

## 研发需求：RD-ADD-02 新材料、独立复核和重新检查

关联功能需求：FR-ADD-02。

### 需求描述

实现补正材料的安全登记与验证边界。当责任人提交补正材料时，系统应根据任务、身份、材料来源与权限生成新引用和处理回执；独立验证人核验真实性、范围与时效，系统记录决定及拒绝原因。只有核验通过且来源输入保持当前有效时，系统才可创建新的 PrecheckRun；仅登记复检意图不改变旧结论，也不关闭任务。

### 数据与状态

| 对象 | 关键引用与处理 | 不变量 |
|---|---|---|
| SubscriptionRemediationCase | sourceFindingId、owner、dueAt、evidenceRule、status | OPEN/IN_PROGRESS/PENDING_VERIFY/COMPLETED 分开；不等于 FR-5 工单 |
| EvidenceReference | evidenceId、来源、上传者、哈希、采集/到期时间、访问级别 | 旧引用只读；新材料有独立证据身份 |
| Verification/PrecheckRun | reviewer、decision、reason、newRunId | 处理人与验证人按规则分离；新 Run 不改旧 Run |

### 验收标准

#### AC1：材料登记

提交新材料后生成独立引用、访问限制与审计记录；只选择旧引用不会形成“新增材料完成”。

#### AC2：独立核验

处理人尝试自验或无权读取证据时拒绝核验，任务仍保持适当非终态。

#### AC3：复检生成

只有验证通过且输入当前有效时才创建新 Run；核验失败返回原因和 Owner，不改变旧 outcome。

#### AC4：并发异常

重复意图幂等返回原回执；任务版本冲突、失效 Finding 或过期证据不产生新的通过结论。

#### AC5：审批交接

新的当前预检与任务处置记录可供审批引用；旧 Run、旧 Finding、材料和独立核验轨迹均可查。

## 研发需求：RD-ADD-03 恢复事实核验与关闭守卫

关联功能需求：FR-ADD-03。状态：待 FR-5 正式需求评审后入库。

### 需求描述

当事件处理人请求恢复核验时，系统应从 FR-4/FR-5 权威来源获取目标范围、控制执行、质量及交付证据，核对采集时间、观察窗、验证人权限与例外决定，保存每目标结论。只有所有必要目标均符合约定恢复规则或取得有权例外，且职责分离与审计成立，才允许进入已恢复/可关闭；未确认、部分成功或仅有说明文字维持待核验。

### 数据与状态

| 对象 | 关键引用与处理 | 不变量 |
|---|---|---|
| RuntimeIncident/WorkItem | impactScope、owner、nextAction、dueAt、status | 处理完成不等于事件关闭 |
| RecoveryVerification | targetId、evidenceRef、observedAt、window、reviewer、result | 各目标独立结论；PARTIAL/UNKNOWN 不聚合成成功 |

### 验收标准

#### AC1：可核验恢复

所有目标证据与观察窗齐备且有权人员核验时，生成固定结论和审计，可进入关闭流程。

#### AC2：说明文字不能代证据

恢复备注出现“已恢复”但无有效证据引用时，核验拒绝且事件保持待核验。

#### AC3：部分与过期

部分目标失败、外部回执缺失或证据过期时，返回逐目标原因，保留未收口清单。

#### AC4：权限与幂等

无权核验、自验违规或重复/迟到回执不会把事件改成成功终态。

#### AC5：复盘交接

关闭前可追溯触发、处置、控制和最高有效证据等级；没有车辆证据时不推断 R3+。

## 四、产品研发需求清单

## 研发需求名称

【订阅申请】-【当前草稿与准入结果】（PG10／FR2-P02～P04）

## 描述

作为 OEM 接入人员，在新申请服务时，我希望看清本申请的权利边界和检查进度，以便安全提交给审批方。

关联功能需求：FR-ADD-01。

## 验收标准

### 1. 功能范围

- 选择服务/权益/能力/范围与期限、保存草稿、运行检查、查看差异、提交申请。

### 2. 页面内容

- 显示结构化对象 ID/Revision、环境、通道、Coverage 类型及可用交集、有效期、检查三维状态和输入/规则版本；跨服务无可复用预检卡片。

### 3. 交互规则

- `新建申请`后显示“尚未检查”；`运行检查`返回本申请 Run；上游变化后显示“结果已失效”并要求重新检查；`提交`前展示当前快照摘要。

### 4. 业务规则

- 只允许当前有效的通过或符合条件的结论提交；范围未知/超界、过期、无权、非本申请 Run 时按钮禁用且服务端拒绝。六态包括加载、空、错误、部分、无权限、冲突。

### 5. 验收结果

- 信号灯与 VRU 两种草稿互不复用发现项；不存在仅更换 ID 却保留示例通过结果的页面；失败保留用户输入并给出修复路径。

## 研发需求名称

【订阅预检】-【补正任务与复检】（PG11／FR2-P06）

## 描述

作为订阅运营人员，在申请被阻断时，我希望明确材料、责任和独立复检结果，以便可信地推进办理。

关联功能需求：FR-ADD-02。

## 验收标准

### 1. 功能范围

- 从 Finding 建任务、提交新材料、请求独立核验、查看核验结果、触发新预检。

### 2. 页面内容

- 显示 sourceFindingId、任务状态、Owner/验证人/期限、所需证据、新旧材料引用、证据权限、最近 Run、下一动作；已知旧引用与新增材料分组展示。

### 3. 交互规则

- `提交材料`只返回登记回执；`请求核验`展示待验证；新 Run 完成后才刷新预检结论；核验失败显示原因、责任和重新提交入口。

### 4. 业务规则

- 自验、无权、过期、任务版本冲突时禁用并返回服务端 denyReason；不以“材料已提交”的 Toast 或复检意图回执关闭任务。六态按 V0.8-04 P06 执行。

### 5. 验收结果

- 一项阻断能追溯到新材料、新验证决定和新 Run；旧 Run 与补正轨迹不被覆盖，未完成时审批仍不能通过。

## 研发需求名称

【运行事件】-【恢复核验与关闭】（PG22，FR-5 待定）

## 描述

作为服务运行负责人，在异常处置后，我希望查看逐目标恢复与独立验证，以便可靠地关闭事件。

关联功能需求：FR-ADD-03；本交付单元须待 FR-5 四层规格、权限矩阵与真实证据契约签认。

## 验收标准

### 1. 功能范围

- 查看影响、处置、恢复事实和未收口目标，发起恢复核验与有权关闭。

### 2. 页面内容

- 列出目标/证据引用/采集时间/观察窗/核验人/结果/例外、事件和 WorkItem 的独立状态与审计时间线。

### 3. 交互规则

- `验证恢复`先显示必要目标与缺失证据；对部分/未知目标展示下一步；`关闭`须二次确认并显示仍未收口的对象。

### 4. 业务规则

### 5. 验收结果
