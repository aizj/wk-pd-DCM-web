# 济南车路云数据上车服务平台端功能合理性审查与深化建议

> 文档版本：V0.3 评审稿  
> 基准日期：2026-09-15  
> 审查对象：《济南车路云数据上车服务平台端对比评估与功能深化方案 V0.2》  
> 审查目的：优先判断功能是否合理、专业、细化，不提前进入高保真UI、技术设计或开发  
> 使用方法：`prd-development`检查“问题—功能—指标—范围—风险”闭环；`epic-breakdown-advisor`检查层级、垂直切片和INVEST；`user-story`抽检是否达到可开发、可验收颗粒  
> 文档关系：本稿是功能专项审查与修正建议，不覆盖V0.1/V0.2；评审确认后再回写正式功能基线。

## 0. 先给判断

### 0.1 一句话结论

**V0.2的功能方向总体合理、专业度较高，但仍属于“完整功能蓝图”，尚未细化到研发可以直接拆票开发的程度。**

问题不在“功能少”，而在：层级口径不统一、P0范围过宽、部分模块仍是名词集合、核心业务规则与异常分支覆盖不均、只有少量功能达到用户故事和验收用例颗粒。

### 0.2 四层评分

| 评价项 | 分数 | 结论 |
|---|---:|---|
| 功能范围合理性 | 8.9/10 | 服务、授权、能力、订阅、配置、发布、证据、运营和安全主链完整，方向正确 |
| 产品架构专业性 | 8.6/10 | 领域对象和状态分离明显优于普通“菜单式方案”，但L1/L2/L3命名仍需统一 |
| 功能细化程度 | 7.1/10 | 已有字段、动作、状态、异常和15项核心规格，但覆盖不均，较多条目仍未形成逐功能规则 |
| 研发交付就绪度 | 5.9/10 | 尚缺完整用户故事、单一When/Then验收、接口前后置、并发/幂等、权限和原因码矩阵 |

换算口径：

- 作为**总体功能蓝图**：约88/100，可进入功能评审；
- 作为**详细产品需求基线**：约72/100，需继续细化；
- 作为**可直接开发的Backlog**：约59/100，不建议立即全量拆工期。

### 0.3 当前客观盘点

| 项目 | V0.2现状 | 审查判断 |
|---|---:|---|
| 功能架构条目 | 44项 | 覆盖广，但多数实际是L2模块，不应全部称L1 |
| 标为P0 | 38项，另有4项P0/P1 | P0膨胀，不能指导取舍和版本计划 |
| 需求条目 | 约30个唯一需求ID | 能追踪方向，尚未覆盖全部L3功能 |
| 产品决策 | 16项 | 边界清楚，是功能深化的良好前提 |
| 核心功能规格 | 15项 | 具备触发/流程/异常/证据，但仍是压缩矩阵 |
| 页面 | 30页 | 页面覆盖完整，但页面数不能替代业务规则 |
| 完整Gherkin场景 | 2个 | 只能证明示例方法，不能证明功能整体可验收 |

## 1. 三套产品经理Skill审查结果

### 1.1 PRD完整性检查

| PRD问题 | 当前结论 | 主要缺口 |
|---|---|---|
| 解决什么问题 | 通过 | 用户痛点主要来自项目经验，真实访谈证据仍需补 |
| 为谁解决 | 通过 | 角色清楚，但每个功能尚未绑定Primary Actor和Decision Right |
| 为什么现在做 | 基本通过 | 政策和量产诉求清楚，项目级商业/运营目标待确认 |
| 建设什么 | 通过 | 功能范围完整，但部分业务域与技术使能项同层 |
| 如何衡量 | 基本通过 | 有北极星、护栏和漏斗；多数单功能尚无局部指标和埋点 |
| 如何验收 | 部分通过 | 15项核心规格＋2个Gherkin不足以覆盖44个模块 |
| 不做什么 | 通过 | S3、Mode B、计费等边界清楚 |
| 依赖与风险 | 通过 | 缺少逐功能依赖、阻塞条件和Owner |

结论：V0.2作为规划PRD结构是完整的；若作为详细功能PRD，需要给每个P0功能补齐“用户、触发、前置、主规则、状态变化、权限、异常出口、事件、指标和验收”。

### 1.2 Epic/功能拆分检查

按INVEST检查，现有44个功能条目不能直接当用户故事：

| INVEST | 当前表现 | 判断 |
|---|---|---|
| Independent | 订阅依赖权益、能力、空间、授权和ICD；发布依赖配置与测试 | 这些是领域Epic/Capability，不是独立Story |
| Negotiable | 大部分保留实现空间 | 通过 |
| Valuable | 订阅、审批、追踪等用户价值明确；编译签名、信任锚等是使能能力 | 使能项应标为Enabler，不伪装成用户故事 |
| Estimable | L3功能和边界未完全列出 | 暂不通过 |
| Small | 单个模块通常包含多个流程、角色和状态 | 不通过 |
| Testable | 少数核心规格可测，多数条目仅有能力描述 | 部分通过 |

适用的拆分模式：

1. **Workflow Steps但采用纵向薄切片**：先完成一个服务、一个OEM、一个区域、一个通道的完整闭环，再增加审批、通道和区域变体；不能按“先做目录、再做API、最后做页面”横向切。
2. **Business Rule Variations**：有效/受限/撤销授权，S0/S1/S2服务，不同风险审批，不同停服原因分别成Story。
3. **Data Variations**：先支持一种CoverageSelector，再按路口、路段、走廊、车道、动态事件区逐类扩展。
4. **Major Effort**：参数注册/有效配置解析先用一个服务打通基础能力，再增加其他服务模板。
5. **Simple/Complex**：单区域、单Uu-A通道、单OEM先闭环；跨区域、多通道去重和复杂迁移后置。
6. **Spike**：Mode B量产车状态上云、跨域地图匹配和极低时延预算属于研究项，不应伪装成确定功能。

注意：安全、授权、租户隔离、审计和与服务等级相关的核心性能不能使用“先能用、以后再安全/再达标”的方式拆分；它们必须进入对应纵向切片的Definition of Done。

### 1.3 User Story/验收检查

现有FN-AUTH-01至FN-OPS-01是“功能规格摘要”，不是完整用户故事。主要缺口：

- 角色虽可推断，但没有逐条写明具体Actor；
- 一个表格单元经常包含多个动作和多个结果，无法直接形成单一When/Then；
- 未为正常、退回、拒绝、撤销、过期、并发更新和重复请求分别建验收场景；
- 未全面定义命令幂等键、版本冲突、审批超时、节点迟到回执和补偿动作；
- 未把权限、审计事件、通知、指标埋点作为每个Story的DoD；
- 部分“系统应支持”缺少可观察的用户结果，需改写为用户能够完成的进展。

因此，当前细化层次应准确称为：

```text
L0 产品平台：已完成
L1 业务域：基本完成，但需重构层级
L2 能力模块：覆盖充分
L3 用户功能：部分完成
L4 User Story＋Gherkin：仅有样例
L5 API/事件/字段/原因码/测试用例：未系统展开
```

## 2. 功能结构存在的专业性问题

### 2.1 P0：层级混用

V0.2把A01—F06共44项称为L1，但其中既有业务领域，也有子模块、页面能力和技术使能项。例如：

- “服务产品”“权益与订阅”是业务域；
- “参数注册表”“订阅调试器”是能力模块；
- “配置编译与签名”“凭证与信任”是技术/安全使能；
- “发布拓扑与漂移”同时像页面、运维能力和领域对象。

修正原则：

```text
L0：产品/平台
L1：稳定业务域，建议6—10个
L2：能力模块，对应清晰Owner和领域对象
L3：用户能执行或系统能完成的原子功能
L4：纵向用户故事＋验收场景
L5：接口、事件、字段、规则、原因码和测试用例
```

### 2.2 P0：优先级没有形成真实取舍

44项中38项直接标P0，另有4项P0/P1，意味着95%以上功能都被表达为首期能力。这样无法回答：

- 哪些是首个闭环必须完整具备的Guardrail；
- 哪些只需最小实现，复杂变体可后置；
- 哪些是规模化运营能力；
- 哪些是探索性能力。

建议不用一个P0标签覆盖整个模块，改用：

| 标记 | 含义 |
|---|---|
| P0-G | 首期不可缺少的授权、安全、审计和失败安全门禁 |
| P0-C | 首个端到端可运营闭环需要的核心能力 |
| P1-S | 多OEM、多区域和日常规模运营能力 |
| P2-E | 未验证、高风险或商业模式相关探索能力 |

### 2.3 P0：功能和页面映射仍偏“菜单思维”

当前页面已经有主操作和异常出口，这是优点；但同一个Job会跨多个页面，尚缺：

- 一条业务流程中谁是主页面、谁是被引用对象；
- 在上下文内完成还是跳转后完成；
- 操作失败后是否保留草稿、回到哪一步；
- 从告警/待办/消息深链进入后如何保持对象和Revision上下文；
- 跨页面是否读取同一个领域状态，还是存在前端复制状态。

### 2.4 P0：核心规则覆盖不均

订阅、配置、发布与追踪写得较深，但以下规则仍需逐功能补齐：

1. 重复申请、并发编辑、版本冲突和幂等；
2. 条件批准、批准附带约束、审批超时、撤回后重提；
3. 环境晋级是复制新实例还是改变原实例；
4. Entitlement收窄时，存量SubscriptionRevision如何精确处理；
5. 多服务组合订阅的依赖、互斥、共享配额和部分批准；
6. ParameterDefinition被废弃时，已生效参数集如何迁移；
7. 同一事件多版本、多通道重复投递和迟到撤销如何裁决；
8. 发布单被暂停后，是继续、重排批次还是必须重建；
9. 节点失联后回执迟到，如何防止旧版本被重新视为有效；
10. 工单恢复与服务自动恢复之间的职责和门禁。

### 2.5 P1：服务通用能力与场景特有能力尚未完全分层

平台不应该为每个场景复制一套订阅、审批和发布功能。建议分成：

- **通用平台能力**：服务、权益、订阅、配置、发布、证据、安全；
- **Service Function Profile**：每个服务声明输入、资格、输出、空间、计算、交付、反馈、降级和准出；
- **场景专属规则/参数**：信号灯、GLOSA、拥堵、VRU、异常停车的差异；
- **OEM能力适配**：车型地图、HMI、算法消费与回执差异。

### 2.6 P1：缺少服务组合但不应过早做计费套餐

OEM可能一次申请信号灯、GLOSA和信号灯提示等关联服务，因此需要`ServiceBundle`或批量申请能力；但它与价格套餐不同：

- ServiceBundle管理依赖、兼容、共同覆盖、共享测试和版本迁移；
- PricingPackage管理价格、折扣、账单和结算；
- 前者可进入P1-S，后者保持P2-E，等待运营与授权模式确认。

### 2.7 P0：V0.2存在五处可复现的一致性缺陷

这些不是表达偏好，而是进入详细PRD前必须修正的模型问题：

| 缺陷 | 现状 | 修正结论 |
|---|---|---|
| 预检失败状态无归属 | 验收样例使用`PRECHECK_FAILED`，但SubscriptionRequest状态表没有该状态 | 新建`PrecheckRun`：QUEUED/RUNNING/PASSED/FAILED/INCONCLUSIVE/STALE；预检失败时Request保持DRAFT或VALIDATING且禁止提交 |
| R0—R6映射不一致 | V0.2未重新定义等级，追溯样例把网关ACK写为R3；V0.1明确网关接受为R2 | 以本稿第2.9节统一词典为唯一口径；所有页面、指标和测试同步引用 |
| 紧急停服前置矛盾 | 同时出现“可先停后补审”和“停发前双人确认” | 拆普通停服与Break-glass：普通停服事前双人审批；已预授权C0由强认证值班员立即执行，自动通知第二复核人并强制事后复核 |
| P0追踪与P1调试器混合 | FN-TRACE-01把事件追踪和五层订阅调试器合成一项；PG12也混为一页 | P0拆为事件证据追踪；P1建设跨授权/订阅/质量/访问/连接的聚合调试器；页面拆PG12A预检结果、PG12B运行调试器 |
| 状态维度仍混用 | SubscriptionInstance含沙箱/灰度；InterestSession含匹配/投递/降级；DeliveryEvidence含阶段/结果/可核验性 | 按第2.8节拆为资格、实例、发布、投递、消费结果、证据评估和健康等独立事实 |

### 2.8 P0：状态模型还需再拆一层

V0.2已经意识到“状态不可混用”，但个别状态族仍混合了不同维度。建议最终模型如下：

| 对象/维度 | 建议状态或字段 | 说明 |
|---|---|---|
| PrecheckRun | QUEUED / RUNNING / PASSED / FAILED / INCONCLUSIVE / STALE | 预检事实独立存在；依赖版本变化后原结果可变STALE |
| QualificationRun | PLANNED / RUNNING / PASSED / FAILED / EXPIRED / INVALIDATED | 沙箱、一致性和准出测试不进入订阅实例状态 |
| SubscriptionInstance | PROVISIONING / READY / ACTIVE / SUSPENDED / EXPIRING / EXPIRED / REVOKED / TERMINATED / FAILED | 只表达可执行订阅实例生命周期 |
| RuntimeInterestSession | CREATED / ACTIVE / EXPIRING / CLOSED / TIMED_OUT / REVOKED | MATCHED属于匹配结果，DELIVERING属于投递，DEGRADED属于服务健康 |
| ReleaseOrder | DRAFT / SCHEDULED / RUNNING / PAUSED / SUCCEEDED / PARTIALLY_SUCCEEDED / FAILED / CANCELLED / ROLLED_BACK | SHADOW/CANARY/ROLLING作为`stage`，不是生命周期状态 |
| DeliveryAttempt | CREATED / ROUTED / SENT / GATEWAY_ACKED / FAILED / EXPIRED / CANCELLED | 描述一次投递尝试，不描述车端是否展示 |
| ConsumptionOutcome | VALIDATED / DISPLAYED / CONSUMED / SUPPRESSED / REJECTED / UNKNOWN | 结果不是严格线性状态；同一事件可有多个受众结果 |
| EvidenceAssessment | evidenceGrade＋verificationStatus | `evidenceGrade=R0—R6`；`verificationStatus=VERIFIED/PARTIAL/UNVERIFIABLE/DISPUTED` |
| ServiceRuntime | controlState＋healthLevel＋recoveryStage | 运行控制、健康等级、恢复阶段三个维度，不压成一个status |
| LegalHold | ACTIVE / RELEASED | 独立冻结关系；Retention/Purge流程检查是否存在ACTIVE Hold |

### 2.9 R0—R6统一证据词典

| 等级 | 统一名称 | 只能证明什么 |
|---|---|---|
| R0 | PRODUCED | 服务事件已生成 |
| R1 | ROUTED | 平台完成目标与通道路由 |
| R2 | GATEWAY_ACCEPTED | RSU网关或OEM/TSP网关接受 |
| R3 | VEHICLE_RECEIVED | 车辆通信终端收到 |
| R4 | VEHICLE_VALIDATED | 车端完成验签、时效、版本和基本语义校验 |
| R5 | PRESENTED | 座舱实际触发展示、语音或触觉 |
| R6 | CONSUMED | 获准车载算法纳入本地处理/决策流程 |

`SUPPRESSED/EXPIRED/REJECTED/CANCELLED`属于Outcome，`UNVERIFIABLE/DISPUTED`属于VerificationStatus，不再作为R0—R6线性末态。HTTP 200、MQ ACK或OEM网关确认最高只能到R2。

### 2.10 P0：六类上车服务自身还没有达到Feature Spec颗粒

V0.2对平台横向能力细化较好，但六类服务当前主要还是“参数域清单”。每个服务必须另有`Service Feature Spec`，至少包含：

1. 目标用户、JTBD、信息/建议/预警等级和禁用用途；
2. 输入DataProduct、权威源、备源、字段血缘和授权边界；
3. ComputePlacement与端到端时间预算；
4. 允许的CoverageSelector、空间版本和地图匹配方法；
5. Eligibility条件、UNKNOWN裁决和抑制规则；
6. 事件产生、更新、合并、撤销、过期和因果关系；
7. Output Schema、语义、reasonCode和版本；
8. TTL、质量门、失败安全和降级输出；
9. 通道、主备、频控、去重、乱序和回落；
10. 目标FeedbackProfile与最高可证明证据等级；
11. OEM HMI、车端算法和ADAS/ADS责任边界；
12. ParameterDefinition、SafetyEnvelope和策略引用；
13. 仿真数据集、异常用例、DVP&R和生产观察指标。

六类服务应继续细化的L3功能如下：

| 服务 | 服务专属L3功能 | 当前成熟度判断 |
|---|---|---|
| 信号灯基础服务 | SPAT源接入与权威性；MAP/路口/Movement/SignalGroup映射；实测/预测标识；时间质量；状态更新/撤销；区域流生成；车端证据 | 较高，但需冻结事件模型、Schema和测量口径 |
| GLOSA | 目标路口/Movement资格；绿灯窗口计算；建议速度区间；法规/项目/车型包络；不确定性表达；动态重算/撤销；效果指标 | 中等，尚不能只用“算法参数”替代完整服务行为 |
| 信号灯上车提示 | 接近区域判断；本车方向/车道相关性；灯态变化触发；频控/去重；过期/撤销；与车端同类提示仲裁 | 中等，需要明确“提示”与基础SPAT数据服务的产品关系 |
| 前方拥堵/队尾风险 | 路段方向；拥堵/队尾识别；严重度；多源融合；持续/更新/解除；路线相关性；信息/风险分级 | 中等偏低，需防止一般拥堵被升格为碰撞预警 |
| 异常停车 | 对象/事件分类；车道/方向定位；持续时间；多源置信；事件合并/拆分；更新/撤销；隐私化输出 | 中等偏低，需补真值、误报治理和撤销闭环 |
| 超视距VRU碰撞风险 | 目标融合；轨迹与时间同步；遮挡关系；冲突区/冲突时刻；风险计算；UNKNOWN/抑制；更新/撤销；边缘/区域部署；隐私输出；S2准出 | 最低且风险最高，应在其他服务闭环后单独评审 |

若没有这六份Service Feature Spec，平台框架虽然专业，但仍不能回答“每类服务具体怎么配、怎么跑、怎么降级、怎么验”。

## 3. 建议重构后的L0—L3功能结构

### 3.1 统一层级

```text
L0  济南车路云数据上车服务运营平台
├── L1-01 服务产品与数据授权
├── L1-02 合作方接入与车型能力
├── L1-03 服务权益与订阅运营
├── L1-04 参数策略与变更治理
├── L1-05 开发接入与联合验证
├── L1-06 发布控制与运行资格
├── L1-07 交付证据与服务运营
└── L1-08 安全审计与平台治理
```

V0.2原A01—F06应整体下沉为L2，不再称为44个L1子系统。

### 3.1.1 业务功能树之外单列T0技术能力视图

以下能力是重要实现支撑，但不与用户功能处于同一层：API网关、事件总线、Schema Registry、规则引擎、工作流引擎、空间计算引擎、配置编译与分发、可观测性平台、KMS/CA、时间同步和数据平台。

每项T0能力必须反向标注支撑哪些L3功能和NFR；但不能用“已建设消息总线/规则引擎”代替“用户业务闭环已完成”。

### 3.2 L1-01 服务产品与数据授权

**核心Job：** 服务产品经理能够证明服务从哪里来、可以提供给谁、输出什么、依赖什么，并安全发布、迁移和退役。

| L2模块 | L3功能ID | L3用户/系统功能 | 关键规则 | 切片 |
|---|---|---|---|---|
| 标准与项目基线 | SP-01 | 查看服务适用的标准/Profile及版本状态 | 区分现行、参考、待实施和项目冻结 | P0-G |
| 数据提供权 | SP-02 | 创建并送审ProvisionAuthority记录 | 平台记录已签认决定，不自行判断合法性 | P0-G |
| 数据提供权 | SP-03 | 校验对象、目的、字段、区域、期限和再提供条件 | 任一必要条件未知时默认阻断 | P0-G |
| 数据提供权 | SP-04 | 预览授权收窄/撤销的下游影响并执行 | 必须精确列出服务、权益、订阅、节点和凭证 | P0-G |

| 数据产品 | SP-06 | 定义QualityPolicy、备源和不可核验状态 | 瞬时事实与策略版本分离 | P0-C |
| 服务产品 | SP-07 | 创建ServiceProduct和不可变ServiceVersion | 已发布版本不可原地覆盖 | P0-C |
| 服务产品 | SP-08 | 配置输入、输出、Scene、Eligibility和依赖 | Service/Scene/Output不得混为一个对象 | P0-C |
| 服务产品 | SP-09 | 发布、弃用、迁移和退役服务版本 | 退役前列出存量订阅迁移及权限收口 | P0-C |
| 服务组合 | SP-10 | 创建ServiceBundle并校验依赖/兼容 | Bundle不是定价套餐；支持部分不可用说明 | P1-S |

| 信任与凭证 | SG-03 | 管理OEM客户端、信任锚、证书状态和吊销联动 | 平台不维护量产VIN主档，但不放弃信任治理 | P0-G |
| 审计 | SG-04 | 记录访问、配置、审批、发布、停服、导出和权限变更 | 审计写入失败触发安全告警/受控降级 | P0-G |
| 数据分类 | SG-05 | 定义字段级分类、用途、精度、脱敏和导出限制 | “无VIN”不自动等于匿名 | P0-G |
| 生命周期 | SG-06 | 配置RetentionPolicy、LegalHold、到期删除和失败工单 | PURGED是数据生命周期状态，不是订阅状态 | P0-G |
| 通知值班 | SG-07 | 管理待办、告警合并、送达、升级和替班 | 通知失败不能静默丢失 | P0-C |
| 业务字典 | SG-08 | 版本化维护状态、原因码、类型和标签 | 页面/API/日志/测试共享同一事实源 | P0-C |
| 平台环境 | SG-09 | 管理组织、时间、地图基线、环境和Feature Flag | 业务运行参数不得塞入系统设置 | P0-G |
| 权限复核 | SG-10 | 定期复核临时授权、离职/协议到期和异常访问 | 复核结论和收口动作可审计 | P1-S |

## 4. 首期应如何真正切片

### 4.1 不建议的横向切法

```text
第一阶段做全部菜单和页面
→ 第二阶段做接口
→ 第三阶段做数据
→ 最后再补权限、审计和异常
```

这种做法每个阶段都无法产生可运营价值，也最容易出现“页面完成、业务未闭环”。

### 4.2 推荐的纵向薄切片

| Slice | 完整价值链 | 必须包含 | 暂缓变体 |
|---|---|---|---|
| S0 学习Spike | 验证未知，不进入生产 | Mode B位置数据、地图匹配、极端时延等明确问题和输出 | 不承诺上线 |
| S1 首个可信闭环 | 一个已获权信号灯服务＋一个OEM应用＋一个车型能力组＋一个区域＋Uu-A | 服务版本、权益、订阅、最小参数集、预检、沙箱、审批、灰度、网关证据、暂停/终止、权限审计 | 多区域、PC5、Bundle、深层回执 |
| S2 证明真正上车 | 在S1上增加车端校验/展示或算法消费证据 | FeedbackProfile、R4—R6、去重、无法核验、对账 | 全量逐事件回执；比例待合规和容量冻结 |
| S3 多场景 | 增加GLOSA、拥堵、异常停车等服务Profile | 不同CoverageSelector、Eligibility、参数、安全等级和准出套件 | VRU S2生产开放 |
| S4 安全预警 | 增加VRU等S2服务的严格门禁 | 边缘优先部署、异常回放、自动暂停、精确停服、联合准出 | 车辆控制/执行S3 |
| S5 规模运营 | 多OEM、多区域、多通道和版本迁移 | 调试器、Bundle、跨区兼容、批量能力、UsageFact | 正式计费套餐 |

所有Slice均包含与其风险相匹配的权限、审计、安全、可观测和失败安全，不能把这些统一推到最后。

### 4.3 S1的Walking Skeleton

```text
数据提供权有效
→ 发布一个ServiceVersion
→ OEM建立Application与车型能力
→ 授予Entitlement
→ 创建并预检SubscriptionRequest
→ 沙箱通过
→ 冻结ParameterSet/Policy
→ 生成并签名ConfigBundle
→ 单区域Canary
→ 节点回报运行哈希
→ 产生事件并收到OEM网关回执
→ 无车端证据时显示无法核验
→ 执行暂停、恢复或终止
→ 导出审计证据
```

这才是P0-C；不是把38个模块的全部高级变体都做完。

## 5. 五个关键Epic的进一步拆分

### 5.1 Epic E1：服务订阅

**原始Epic：** OEM能够申请、审批、验证、激活、变更和终止数据上车服务。

采用模式：Workflow＋Business Rule Variation＋Simple/Complex。

| Story顺序 | 纵向Story | 用户价值 |
|---|---|---|
| E1-S1 | 一个有权OEM对一个服务/车型/区域完成申请—预检—审批—沙箱—激活 | 首次实现完整可用订阅，而非只建申请表 |
| E1-S2 | 预检发现授权/能力/空间/ICD阻断并可补正重提 | 减少线下往返且避免错误开通 |
| E1-S3 | 条件批准并把条件固化为机器策略 | 审批意见不会停留在文字里 |
| E1-S4 | 创建新Revision完成扩缩容和有序切换 | 生产修改可回滚、不覆盖历史 |
| E1-S5 | 权益撤销触发精确停发和权限收口 | 合规变化能安全退出 |
| E1-S6 | 多服务Bundle或批量申请 | 多服务规模运营；P1-S |

### 5.2 Epic E2：参数与有效配置

采用模式：Major Effort＋Data Variation。

| Story顺序 | 纵向Story | 用户价值 |
|---|---|---|
| E2-S1 | 为一个信号灯服务定义参数、包络、参数集并查询最终值 | 配置员首次能解释“为什么是这个值” |
| E2-S2 | 检测越界和继承冲突并阻断送审 | 错误配置不进入审批 |
| E2-S3 | 比较现行/草稿并列出影响对象 | 审批人理解爆炸半径 |
| E2-S4 | 对配置执行回放并关联报告 | 参数有验证证据 |
| E2-S5 | 增加区域/OEM/车型/订阅绑定变体 | 支持规模化差异配置 |
| E2-S6 | 增加受控实验和自动失效 | P1-S，不绕过安全包络 |

### 5.3 Epic E3：灰度发布与回滚

采用模式：Workflow＋Business Rule Variation。

| Story顺序 | 纵向Story | 用户价值 |
|---|---|---|
| E3-S1 | 单区域单批次从签名包到节点运行哈希形成闭环 | 能证明配置真正生效 |
| E3-S2 | 节点拒绝/不可达时显示部分生效并自动暂停 | 不把部分失败包装为成功 |
| E3-S3 | 引用历史良好版本完成可审计回滚 | 失败可安全恢复 |
| E3-S4 | 授权撤销/严重风险触发精确Kill Switch | 紧急止损不等待维护窗 |
| E3-S5 | 根因关闭后通过恢复门禁 | 防止故障未消除就自动恢复 |
| E3-S6 | 多区域兼容窗口和双版本协同 | P1-S，限制全局爆炸半径 |

### 5.4 Epic E4：交付证据与订阅调试

采用模式：Data Variation＋Simple/Complex。

| Story顺序 | 纵向Story | 用户价值 |
|---|---|---|
| E4-S1 | 从数据源到OEM网关ACK展示单事件时间线 | 能证明城市侧和网关侧事实 |
| E4-S2 | 无车端回执时明确最高证据和无法核验原因 | 不把ACK当作已上车 |
| E4-S3 | 接收车端校验/展示/消费回执并去重关联 | 能证明更深层达成 |
| E4-S4 | 授权—订阅—质量—访问—连接五层诊断 | 快速定位“为什么没数据” |
| E4-S5 | 双方批次对账、争议和证据导出 | 支持运营结算准备和责任澄清 |

### 5.5 Epic E5：安全与数据生命周期

采用模式：Business Rule Variation；属于每个纵向Slice的Guardrail，不单独拖到末期。

| Story顺序 | 纵向Story | 用户价值 |
|---|---|---|
| E5-S1 | 不同租户/环境只能访问获权对象 | OEM和城市避免跨租户泄露 |
| E5-S2 | 高风险编辑人不能自审自发 | 防止单点错误进入生产 |
| E5-S3 | 审计写入失败触发阻断或受控降级 | 关键操作不会无证执行 |
| E5-S4 | 到期数据按分类策略删除，Legal Hold例外留证 | 保留与删除均可证明 |
| E5-S5 | 凭证吊销精确影响端点、订阅和节点 | 安全事件可快速收口 |

## 6. User Story＋Gherkin抽检样例

以下样例遵循“一条Story一个主要When和一个主要Then”。复杂结果拆成不同场景，而不是在一个Story中堆叠所有分支。

### US-SUB-01：完成首个可执行订阅申请

- **As a** OEM服务接入负责人
- **I want to** 为已确认车型能力组提交一个限定服务、区域和通道的订阅申请
- **so that** 双方能够基于同一份不可变契约开展验证和生产准入

**Scenario：符合条件的订阅申请提交成功**

- **Given** OEM主体、应用环境、车型能力和ServiceEntitlement均有效
- **And Given** 所选CoverageSelector、ICD、质量和通道预检无阻断项
- **When** 接入负责人提交订阅申请
- **Then** 平台生成不可变申请Revision并进入`SUBMITTED`，同时保留人类可读契约摘要和机器策略摘要

### US-SUB-02：提供权缺失时获得可执行补正路径

- **As a** OEM服务接入负责人
- **I want to** 在订阅被阻断时看见具体事实和补正责任
- **so that** 我能推动正确责任方处理，而不是反复线下询问

**Scenario：数据提供权不覆盖目标OEM**

- **Given** 其他能力和接口条件均满足
- **And Given** ProvisionAuthority不包含该OEM或所选用途
- **When** 接入负责人运行生产订阅预检
- **Then** 平台将本次PrecheckRun置为`FAILED`，保持申请草稿且禁止提交，并提供规则编码、证据、责任方和“发起补证”入口

### US-CONF-01：解释某订阅最终生效配置

- **As a** 配置运营人员
- **I want to** 查询指定订阅、区域、车型和时间的最终参数值及来源
- **so that** 我能在送审前确认配置没有被错误继承或覆盖

**Scenario：解析无冲突的有效配置**

- **Given** 服务默认、区域Profile、车型能力和订阅Revision均有有效版本
- **When** 配置运营人员查询目标时间点的EffectiveConfig
- **Then** 平台返回不可变快照，逐字段展示最终值、来源层级、作用域、版本和哈希

### US-REL-01：节点部分生效时安全暂停发布

- **As a** 生产发布管理员
- **I want to** 在任一关键节点未运行目标版本时自动暂停后续批次
- **so that** 部分失败不会被当作成功扩散到更大范围

**Scenario：Canary批次存在不可达节点**

- **Given** 发布单正在执行Canary且一个关键节点在观察窗内未回报目标运行哈希
- **When** 发布门禁评估本批次结果
- **Then** 平台把ReleaseOrder置为`PAUSED`并记录本阶段结果为`PARTIALLY_SUCCEEDED`，停止后续批次，同时展示未知影响范围和回滚入口

### US-TRACE-01：不把网关ACK当作车辆已使用

- **As a** 服务运营和审计人员
- **I want to** 看见一次服务事件能够证明的最高车端证据层级
- **so that** 对外报告不会夸大数据已经展示或被算法消费

**Scenario：只有OEM网关回执**

- **Given** 事件已由OEM网关确认但没有有效车端校验、展示或消费回执
- **When** 运营人员查看事件详情和达成漏斗
- **Then** 平台最高只展示`R2 / GATEWAY_ACCEPTED`并将R3—R6标为`UNVERIFIABLE`及其原因

### US-STOP-01：授权撤销后精确停发

- **As a** 有权的数据授权/安全负责人
- **I want to** 在授权撤销时按服务、OEM和区域精确停止新投递
- **so that** 未授权服务不会继续运行，也不会无故扩大停服范围

**Scenario：授权对象被正式撤销**

- **Given** 撤销决定已被有权主体签认且影响分析已定位下游对象
- **When** 授权负责人执行紧急撤销
- **Then** 平台生成不可变停服命令并仅对受影响范围停止新匹配，同时保留节点回执和事后复核任务

## 7. 每个P0功能必须补齐的规格字段

### 7.1 Definition of Ready

进入设计/开发前，每条P0 Story至少具备：

- 具体用户或系统Actor，不能只写“用户”；
- 对应JTBD和可观察结果；
- 前置对象及其版本/状态；
- 单一主命令或触发事件；
- 输入字段、来源、必填、类型和校验；
- 正常状态迁移和可重试边界；
- 权限Scope、职责分离和租户/环境约束；
- 至少一个正常、一个阻断、一个恢复/退出场景；
- 输出对象、领域事件、通知和审计记录；
- 幂等键、并发版本和重复提交处理；
- 指标/埋点及“无法核验”口径；
- 依赖、假设、开放问题和Owner；
- 一个When/Then可验证的验收用例。

### 7.2 Definition of Done

- 正常、异常、边界、权限、并发和重放用例通过；
- 页面/API/事件/审计对同一业务ID和状态含义一致；
- 失败不会把对象静默置为成功；
- 审计、监控、告警和原因码可查询；
- 回滚或安全退出路径完成演练；
- 涉及数据的分类、用途、保留和导出规则生效；
- 依赖版本和测试证据可追溯；
- 文档、Schema、字典和兼容矩阵同步发布；
- 对无法获取的车端事实明确显示`UNVERIFIABLE`；
- QA能够仅依据Story和引用规格判断通过/失败。

## 8. 功能评审应使用的十问

以后每评审一个模块，不先问“页面长什么样”，先回答：

1. 哪个具体角色在什么情境下使用？
2. 他要完成的进展是什么，而不只是点哪个按钮？
3. 这个功能依赖哪些有版本和状态的领域对象？
4. 用户发出的主命令是什么，是否幂等？
5. 成功后哪个对象从什么状态变成什么状态？
6. 谁能编辑、谁能审批、谁能发布、谁只能查看？
7. 数据缺失、权限不足、版本冲突、依赖异常时从哪里退出？
8. 系统发出什么领域事件、通知和审计证据？
9. 怎样证明功能有效，怎样表示无法核验？
10. 它属于首个完整纵向Slice，还是规模化变体/探索项？

任何一项答不上来，功能仍处于“能力描述”，还不是可开发需求。

## 9. 本轮建议的功能评审顺序

不建议一次评完全部80余个L3功能。按风险和主链分五轮：

| 轮次 | 评审范围 | 目标 |
|---|---|---|
| FR-1 | 服务产品、数据提供权、车型能力、Entitlement | 冻结“谁有权、谁有能力、提供什么” |
| FR-2 | 订阅申请、预检、审批、实例、Revision和退出 | 冻结服务契约和生命周期 |
| FR-3 | 参数注册、安全包络、策略、有效配置、变更审批 | 冻结“什么值为何生效” |
| FR-4 | 沙箱准出、配置包、灰度、节点、停服、回滚和恢复 | 冻结生产变更安全闭环 |
| FR-5 | 数据质量、事件追踪、回执、对账、工单和指标 | 冻结“真正上车”的证据闭环 |

安全、权限、审计、数据生命周期作为每轮横向Guardrail同步评审，不单独留到最后。

### 9.1 每轮交付物

1. 领域对象/状态变化图；
2. L3功能清单及Actor、输入、输出、规则、异常；
3. 纵向故事地图和P0-C/P0-G/P1-S切片；
4. User Story＋Gherkin；
5. 页面入口、上下文动作和异常出口；
6. API/事件/字段/原因码引用；
7. 指标、审计和验收用例；
8. 开放问题、Owner和阻塞门禁。

## 10. 最终建议

### 10.1 是否合理

合理。主链和责任边界没有根本性缺陷，尤其是三层订阅、状态族分离、参数有效值、灰度/回滚和R0—R6证据方向是正确的。

### 10.2 是否专业

达到高级产品规划专业度，但要把V0.2的44个“L1”重构为8个L1业务域＋L2模块，否则架构层级会在后续PRD、菜单、微服务和团队分工中被不同理解。

### 10.3 是否足够细化

**还没有。** 当前细化足以做功能架构评审，不足以直接进入全量开发。最明显证据是：38/44模块都标P0、仅15项压缩功能规格、仅2个完整Gherkin场景。

### 10.4 立即下一步

先评审并确认本稿的8个L1业务域和S1 Walking Skeleton。确认后，从FR-1开始，为P0-C/P0-G功能建立正式的“L3功能规格＋L4 User Story＋L5验收/接口引用”，而不是继续增加菜单和功能点数量。
